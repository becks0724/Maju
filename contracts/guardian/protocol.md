# 운전자 무응답 확인(가칭) 중계 프로토콜 (contracts/guardian)

차 앱(Pleos, `:car`) · 휴대폰 앱(`:phone`) · 워치 앱(`:watch`)과 중계 서버(`server/guardian-relay/relay.py`)가 이 문서를 같이 따른다. 공유 모델은 `apps/guardian/shared`(`:shared` protocol), 서버 구현과 시험은 `server/guardian-relay/` 에 있다. 규격을 바꿀 때는 이 문서를 먼저 고치고 두 구현의 시험을 다시 통과시킨다.

근거는 설계 `docs/design/design-v1.md` §2 · §7 · §12(v1.1 워치 직접 경로)와 팀 내부 법 준수 지침(비공개 · README 「안전 · 개인정보 원칙」에 요약) G2 · G3 · G4 · G9 다.

2026-11-01 고침 — 차 화면 생체 표시 설정 `carDisplay`(§4.1 · §5 · §8)와 차 → 휴대폰 테스트 요청 `TEST_REQUEST`(§4.6 「차에서 테스트 요청」)를 더했다(설계 `docs/design/car-spec.md` §8 · §9-2 · §9-3 · §12, 사용자 결정 2026-11-01 「권장안대로」).

## 1. 왜 이 모양인가

- 차 앱은 푸시를 받을 수 없다. 그래서 모든 쪽이 정해진 주기로 `POST .../sync` 를 보내고, **응답에 상대의 최신 상태와 나에게 온 지시를 실어** 받는다(긴 폴링 · 웹소켓 · FCM 없음, 계정 · 외부 서비스 불필요).
- 중계는 판정하지 않는다. 짝을 맺고, 쪽마다 최신 상태 1건을 보관하고, 지시를 받는 쪽 큐에 넣어 ack 될 때까지 다시 보낸다. 판정은 `:shared` 상태 기계가 차(또는 대신 휴대폰)에서 한다.
- 워치는 휴대폰을 거쳐(Wearable Data Layer) 오거나, 중계에 직접 붙는다(`/v1/watch/sync`). Galaxy Watch9 는 Android 13 이상 휴대폰만 짝이 되므로 Android 12 인 Note10+ 와는 직접 경로가 필요할 수 있다(설계 §12).
- **워치가 받는 지시는 직접 경로로만 닿는다**(PM 결정 2026-10-30). Data Layer 는 워치 → 휴대폰 상태 데이터만 나르는 보조 경로다(§4.7).

권장 주기는 차 2초, 휴대폰 2초(사건이 생기면 즉시 한 번 더), 워치 직접 2초다 [추정 — 배터리 · 실측으로 조정].

## 2. 전송

| 구분 | 주소 | 전송 | 비고 |
|---|---|---|---|
| 베타(지금) | Mac 에서 도는 `relay.py`, 포트 8095 | **LAN 평문 HTTP** | 같은 Wi-Fi 한정. 앱은 debug 빌드에서 설정한 주소만 평문을 허용(network security config). Pleos 에뮬레이터는 `http://10.0.2.2:8095` |
| 운영(공개) | 정하지 않음(사용자 결정) | **HTTPS 만** | Pleos 보안 가이드 · G2. 평문 주소는 release 빌드에 넣지 않는다 |

- 모든 요청 · 응답 본문은 UTF-8 JSON 객체다. 요청 헤더 `Content-Type: application/json`.
- 요청 본문 상한은 **64KB** 다. 65,536 byte 까지 받고, 65,537 byte 부터 413.
- 응답 헤더에 `Cache-Control: no-store`. **모든 응답 뒤 서버가 연결을 닫는다**(`Connection: close`, 2026-11-14 합동 점검 D-3 — 한 연결에 이어 붙인 요청이 다음 요청으로 읽히는 끼어들기를 막음). 클라이언트는 요청마다 새 연결을 쓴다. `Content-Length` 는 ASCII 숫자만(부호 · 0x · 다른 숫자 꼴은 400), `Transfer-Encoding` 이 있으면 400, `GET /v1/health` 에 본문이 있으면 400.
- 시각은 모두 **밀리초 정수**다. `serverTime` · `receivedAt` 은 중계 시계(유닉스 에포크 ms)다. **중계는 나이 · 만료를 단조 시계로 잰다**(2026-11-13, 레드팀 발견 6 · 2026-11-14 C-4 — 잠자기도 세는 시계: Linux `CLOCK_BOOTTIME`, macOS `clock_gettime(CLOCK_MONOTONIC)`, 둘 다 없으면 `time.monotonic`. 중계 Mac 이 잠들었다 깨도 묵은 지시 · 상태가 신선하게 보이지 않는다) — `serverTime` 은 응답을 만든 순간의 벽시계이고, 응답에 싣는 `receivedAt` 은 `serverTime − (단조 시계로 잰 받은 뒤 경과)` 다. 그래서 같은 응답 안의 `serverTime − receivedAt` 과 `ageMs` · `watchDirectAgeMs` 는 중계 벽시계가 뒤로 · 앞으로 바뀌어도 **늘 0 이상이고 실제 경과와 같다**. 벽시계가 바뀌지 않는 동안 `receivedAt` 값은 받은 순간의 벽시계와 같아 뜻이 그대로다. 벽시계가 바뀐 뒤에는 같은 상태의 `receivedAt` 이 응답마다 바뀐 폭만큼 함께 움직인다(다른 응답의 `serverTime` 과 견주는 쪽 — 휴대폰 철회 대기 `LastSyncWait` — 은 그 순간 한 번 어긋날 수 있다). 짝 24시간 · 번호 10분 · 지시 `ttlMs` · 빈도 제한 창도 단조 시계라 벽시계와 무관하다. `sentAt` · `at` · `lastPulseAt` · `responseAt`(워치 · 휴대폰) 은 보낸 기기의 벽시계(에포크 ms)로, 사람이 읽는 시각 · 기록용이다. 특히 **`responseAt` 은 증가 표시 전용**이다 — 받는 쪽은 값을 다른 시계와 빼지 않고 「이전 값보다 1초 넘게 커졌는지」만 본다(§4.3, 2026-10-30).
- **판정 타이머는 단조 시계로 잰다**(PM 결정 2026-10-30, `:shared` ClockOffset · FlowMachine 주석). 앱은 상태 기계 입력 시각과 시계 보정에 `SystemClock.elapsedRealtime`(부팅 뒤 경과 ms)을 쓴다. 로컬 표시 사건 id `event-L{ms}` 의 숫자는 에포크가 아니라 **보낸 기기의 단조 시각**이다.
- **sync 에 싣는 flow 의 시계는 규칙 하나다**(2026-10-30 — 평소 sync 와 넘김이 달라 차가 휴대폰 스냅숏을 그대로 이어받지 못하던 것을 정리). 보낸 쪽에 시계 보정값이 있으면 **늘 중계 시각**(`snapshot.clock:"SERVER"`), 보정값이 없을 때만 보낸 기기 단조 시각(`"LOCAL"`)으로 싣는다(`:shared` `FlowStatus.forSync`). 평소 sync · 주인 넘김 · `FLOW_SNAPSHOT` 이 모두 같다. 받는 쪽은 늘 `restoreLocal` 로 되돌린다 — 예(차가 휴대폰 flow 를 받을 때).

  ```kotlin
  val r = res.peer?.flow?.restoreLocal(offsetMs = carClock.offsetAt(nowMono), nowLocalMs = nowMono)
  // SERVER + 내 보정값 → 정확히 · 다른 기기의 LOCAL 또는 내 보정값 없음 → 늦어지는 쪽으로 재기준(r.clockVerified == false)
  // 설정(snapshot.powerOn · consents · test)은 시계와 무관하게 그대로 읽힌다
  ```
 기기 시계와 중계 시계, 서로 다른 기기의 단조 시각을 섞어 빼지 않는다.

## 3. 엔드포인트

| 메서드 · 경로 | 보내는 쪽 | 요청 | 성공 응답(200) |
|---|---|---|---|
| `GET /v1/health` | 누구나 | 없음 | `{"ok":true}` |
| `POST /v1/pair/start` | 차 | `{}` 또는 빈 본문 | `{"pairCode":"123456","carToken":"<hex32>","expiresInSec":600}` |
| `POST /v1/pair/code` | 차 | `{"token":"<carToken>"}` | `{"pairCode":"654321","expiresInSec":600}` |
| `POST /v1/pair/join` | 휴대폰 · 워치 | `{"pairCode":"123456","role":"PHONE","requestId":"<1~64자, 선택>"}` | PHONE → `{"phoneToken":"<hex32>","pairId":"<hex16>"}` · WATCH → `{"watchToken":"<hex32>","pairId":"<hex16>"}` |
| `POST /v1/car/sync` | 차 | CarSyncRequest | CarSyncResponse |
| `POST /v1/phone/sync` | 휴대폰 | PhoneSyncRequest | PhoneSyncResponse |
| `POST /v1/watch/sync` | 워치(직접 경로) | WatchSyncRequest | WatchSyncResponse |
| `POST /v1/pair/end` | 누구나 | `{"token":"<hex32>"}` | `{}` |

### 3.1 짝짓기

- 차가 `pair/start` 로 6자리 숫자 코드(무작위, 앞자리 0 가능 — 문자열로 다룬다)와 `carToken` 을 받는다. 차 화면에 코드를 보여 준다.
- 휴대폰 · 워치가 코드를 입력해 `pair/join` 한다. `role` 은 `"PHONE"` 또는 `"WATCH"`, 생략하거나 null 이면 `"PHONE"`(선택 필드 규칙, 2026-11-08).
- 코드는 **10분** 뒤 만료되고, **역할마다 한 번만** 쓴다(휴대폰 한 번 · 워치 한 번). 두 역할이 모두 쓰면 코드는 바로 없어진다. 만료 · 없는 코드 · 이미 쓴 역할은 모두 같은 오류(404 `PAIR_CODE_INVALID`)로 답해 어느 쪽인지 드러내지 않는다.
- 토큰은 `secrets.token_hex(16)`(무작위 128비트, 소문자 16진 32자), `pairId` 는 `secrets.token_hex(8)`(16자)이다. `pairId` 는 표시 · 기록용이고 인증에 쓰지 않는다.
- 짝은 `pair/start` 시각부터 **24시간** 뒤 사라진다(sync 로 늘어나지 않는다). 그 뒤 모든 토큰은 401. 앱은 다시 짝을 맺는다.
- 토큰은 역할에 묶인다. 휴대폰 토큰으로 `car/sync` 를 부르면 401 이다.
- **참여 멱등(2026-11-14 · D-4 판2-4)** — `pair/join` 의 선택 `requestId`(1~64자 문자열, 틀리면 400)는 앱이 참여 시도마다 만들고 **다시 시도할 때 그대로** 쓴다. 같은 번호 · 같은 역할 · 같은 `requestId` 면 처음 준 응답(같은 토큰)을 다시 주고 실패로 세지 않는다(그 토큰이 아직 그 역할의 토큰일 때, 번호 만료까지). 참여 응답이 유실된 뒤 다시 시도하면 404 가 나던 것을 막는다. 토큰을 다시 받는 것은 번호와 `requestId` 를 둘 다 가진 쪽뿐이다. 없으면 지금 규칙이다. **지금 휴대폰 · 워치 앱은 `requestId` 를 보내지 않는다** — 중계 쪽만 준비되어 있어, 참여 응답이 유실되면 앱에서는 여전히 404 가 나고 차에서 번호를 새로 받아야 한다(2026-11-14 재검증에서 확인, 앱 반영은 제출 뒤).
- **남은 시간은 사실대로** — 참여한 적 없는 짝은 첫 번호가 만료되면 지워지므로, 그 짝의 `pair/code` 새 번호는 `expiresInSec` 이 첫 번호 만료까지 남은 초(10분 이하)다.
- **새 코드(다시 붙이기)** — 차는 `pair/code` 로 같은 짝의 새 코드를 받는다(워치를 바꿨거나 워치 연결을 끊은 뒤 등). 새 코드를 받으면 그 짝의 이전 코드는 없어진다(짝마다 살아 있는 코드는 하나). 새 코드도 10분 만료 · 역할마다 한 번이다. 짝의 24시간은 늘어나지 않는다. 차 토큰만 쓸 수 있다(그 밖은 401).
- **다시 참여(2026-11-08 바뀜 — 휴대폰 재설치 뒤 24시간 다시 짝지을 수 없던 것, 11-02 리뷰 중 8)** — 새 코드로는 **이미 참여 중인 역할도** 다시 붙는다. 그러면 중계는 그 역할의 새 토큰을 내주고 **옛 토큰은 그 순간부터 401**(sync · `pair/end` 모두)이다. 차 토큰 · 짝 · 다른 역할 토큰은 그대로이고, 그 역할의 최신 상태 · 받을 지시 큐는 지우지 않는다(새 기기가 이어받는다). 그 역할의 seq 기준은 비운다(§5). `pair/start` 의 첫 코드는 이전처럼 역할마다 한 번이라, 같은 코드로 같은 역할이 다시 붙지는 못한다(차가 `pair/code` 로 새 코드를 받아야 한다).
- 중계는 짝을 **최대 64개** 둔다. 매 요청 처리 전에 ① 24시간이 지난 짝을 만료가 이른 것부터, ② **참여한 역할(휴대폰 · 워치)이 하나도 없고 살아 있는 코드도 없는 짝**(코드가 10분 만료된 뒤 아무도 안 붙은 짝, 2026-11-08 추가 — 무인증 `pair/start` 로 자리를 24시간 채우지 못하게)을 지운다. ③ **한 번도 참여한 적 없는 짝은 첫 코드(`pair/start`)가 만료되는 순간(`pair/start` 뒤 10분) `pair/code` 로 새 코드를 받았어도 지운다**(be-qa · PM 결정 2026-11-08 — 새 코드를 거듭 받아 빈 짝을 붙잡는 길을 막는다). 한 번이라도 휴대폰 · 워치가 참여한 짝의 `pair/code`(다시 참여 · 워치 추가)는 ②만 따른다(코드가 사는 동안 남는다). 그래도 64개면 살아 있는 짝은 밀어내지 않고 503 `CAPACITY` 로 답한다(쓰는 중인 연결을 끊지 않으려고). ② · ③으로 지워진 짝의 차 토큰은 401 이고, 차는 다시 `pair/start` 한다. 상한 64 는 `--max-pairs` 로 바꿀 수 있다.

#### 3.1.1 남용 제한(2026-11-13 — 공개 호스팅 요건, 보안 감사 중3)

짝짓기 경로에 건다. **sync 는 토큰마다 2초에 30번**(`--sync-per-token` · `--sync-window-sec`, 2026-11-14 D-3 — 정상 몰림은 2초에 6번 안팎)까지이고, 넘으면 429 다(앱의 문자 보낼 함이 지시를 남긴다). **주소 키(프록시 뒤면 `X-Forwarded-For`) 하나가 동시에 처리받는 요청은 16개**(`--concurrent-per-addr`, 머리를 읽은 뒤 셈, 켜 둠)까지이고, 넘으면 429 다. `pair/end` · `/v1/health` 에는 빈도 제한이 없다. 제한에 걸리면 **429 `RATE_LIMITED`** 로 답하고 짝 · 토큰 · 상태는 그대로 둔다 — **새 제한은 401 을 내지 않는다**(앱은 401 만 짝 폐기로 다룬다). 예외는 아래 「주소별 짝 상한」이 밀어내는 조용한 짝 하나다 — 그 짝의 토큰은 그 뒤 401 이다. 「주소」는 보낸 쪽 주소다(기본 소켓 주소, `--trust-proxy` 일 때만 `X-Forwarded-For` 의 마지막 값, IPv6 는 /64 로 묶고 `pair/join` 실패만 /48 로 묶음). 값은 모두 명령줄로 바꿀 수 있고, 아래는 기본값이다.

| 대상 | 세는 것 | 문턱(기본) | 걸리면 | 풀림 |
|---|---|---|---|---|
| `pair/join` | 주소마다 실패(404 `PAIR_CODE_INVALID` — 틀린 · 만료 · 이미 쓴 번호). IPv6 는 /48 마다 | 10분 안 10번 | 그 주소의 `pair/join` 을 **맞는 번호까지** 429 | 10분 뒤 |
| `pair/join` | 살아 있는 번호 하나에 걸린 실패(그 번호에 이미 쓴 역할로 다시 참여) | 5번 | 그 번호를 버린다(만료와 같음, 404) | 차가 `pair/code` 로 새 번호 |
| `pair/code` | 짝마다 요청 | 10분 안 10번 | 429 | 창이 밀려나면 |
| `pair/code` | 주소마다 요청 | 10분 안 20번 | 429 | 창이 밀려나면 |
| `pair/start` | 주소마다 요청 | 1분 안 10번 | 429 | 창이 밀려나면 |
| `pair/start` | 주소마다 살아 있는 짝(그 주소가 `pair/start` 로 만든 짝) | 8개(시연 기본 — 공개 운영 값은 README) | 그 주소의 **조용한 짝**(차 · 휴대폰 · 워치 **모두** sync 가 없고 `pair/join` · `pair/code` 도 없음 — 참여한 적 없는 짝은 2분, 참여한 적 있는 짝은 10분) 하나를 지우고 받는다 — 참여 안 한 짝 먼저, 그다음 가장 오래 조용한 짝. 조용한 짝이 없으면 429 | 짝이 끝나거나(`pair/end` · 만료) 조용한 짝이 생기면 |
| `pair/start` | 서버 전체 살아 있는 짝 | 64개 | 503 `CAPACITY` | 짝이 만료 · 종료되면 |

- 성공한 참여는 주소의 실패 수를 지우지 않는다(제 짝을 만들어 참여하는 것으로 계수기를 비우지 못하게). 막힌 요청은 세지 않는다.
- **주소별 짝 상한이 밀어내는 짝(2026-11-13 검증 지적 · 재검증으로 고침)** — 차 앱은 토큰이 없을 때만 `pair/start` 한다. 그래서 같은 주소에 차가 옛 짝을 남기는 길은 차 앱 재설치 · 데이터 지우기 · `pair/end` 실패(「휴대폰 연결 끊기」의 끝내기가 중계에 닿지 못함)다. 다만 주소를 나눠 쓰는 다른 집 · 다른 차의 짝도 같은 주소의 짝으로 세어진다. 그래서 중계는 「버려짐」을 차 sync 하나로 보지 않고, **세 역할 어느 쪽이든 sync 한 마지막 시각**으로 본다. 차가 주차 · 터널 · 음영으로 조용해도 휴대폰이나 워치가 sync 하는 짝은 밀려나지 않는다. 참여한 적 있는 짝은 문턱을 10분으로 길게 둔다(세 기기가 모두 잠시 망을 잃는 경우를 견디게).
  - 밀려난 짝은 **되살아나지 않는다**. 그 짝의 차 · 휴대폰 · 워치는 다음 sync 에서 401 을 받아 기기 쪽 짝을 지운다. 차는 스스로 `pair/start` 해 새 번호를 띄우지만, 휴대폰 · 워치는 **사용자가 차 화면의 새 번호를 넣어 다시 짝지어야** 한다(자동으로 다시 붙지 않는다).
  - 같은 주소의 공격자는 조용한 짝만 지울 수 있다. 이웃 짝이 세 기기 모두 2분(미참여) · 10분(참여) 넘게 조용할 때만이다.
- **프록시 헤더 해석(2026-11-14 · D-4 보2-3)** — `--trust-proxy` 일 때 `X-Forwarded-For` 의 마지막 값은 「주소」 · 「주소:포트」 · 「[v6]」 · 「[v6]:포트」 꼴을 읽는다. 없거나 해석이 안 되면 주소 없이 `xff_bad` 로 세고 소켓 주소를 쓴다. 소켓 상대가 루프백이 아니면 헤더를 보지 않는다. `--trust-proxy` 와 루프백이 아닌 `--bind` 를 함께 주면 시작하지 않는다.
- **분 단위 계수 줄(D-4 · 보안 13)** — 60초마다 주소 · 토큰 없이 한 줄을 남긴다: 상태 코드별 개수, `join_fail` · `xff_bad` · `evicted`(밀어낸 짝) · `seq_stale`(덮지 않은 늦은 seq) 개수, 짝 · 번호 · 연결 수, 최대 처리 시간. 404 가 분당 30, 429 가 60, 짝이 상한의 80% 를 넘으면 `WARN` 을 붙인다. `seq_stale` 은 응답에 싣지 않는다(sec-audit — 진짜 값의 위치를 좁히지 못하게).
- 계수기는 종류마다 주소 · 짝을 최대 4,096개(`--max-keys`) 기억한다. 꽉 차면 창이 지난 것을 먼저 치우고, 그래도 꽉 차면 **막히지 않은 키 가운데 마지막 사건이 가장 오래된 것을 밀어내고** 새 키를 받는다(막힌 키는 남긴다, 2026-11-13 바뀜 — 처음 보는 주소를 막던 설계는 계수기를 채워 정상 사용자를 막는 통로였다). 처음 보는 주소는 꽉 찼어도 막히지 않는다. 모든 키가 막혀 있으면 새 주소는 세지 못한다(막지도 않는다).
- 통합 시험의 `FakeRelay`(`apps/guardian/integration/.../FakeRelay.kt`, 앱 동결로 고치지 않음)는 이 절의 429 빈도 제한 · 주소별 짝 상한 · 단조 시계(§2) · 연결 상한 · 읽기 마감(§7)을 흉내 내지 않는다. 이 차이는 서버 시험(`server/guardian-relay/test_limits.py`)만 고정한다.
- 보낸 쪽 주소는 메모리의 계수기에만 두고 로그 · 응답에 남기지 않는다(§8).

### 3.2 짝 끝내기

- 차 · 휴대폰 토큰으로 `pair/end` → 짝 전체(차 · 휴대폰 · 워치 토큰, 상태, 큐, 남은 코드)를 지운다.
- 워치 토큰으로 `pair/end` → **워치 연결만** 지운다(워치 토큰 · 워치 직접 상태 · 워치 큐). 차 · 휴대폰 짝은 남는다. 단 휴대폰이 없는 짝은 워치가 끊고 살아 있는 코드도 없으면 §3.1 의 정리 규칙으로 짝 전체가 지워진다(차 토큰 401).
- **동의 거부 · 철회와 앱 「모두 지우기」, 차의 「휴대폰 연결 끊기」 때만** 앱은 `pair/end` 를 부른다(G2 철회 시 삭제). 차는 확정 정지(기어 P — 주차 브레이크만으로는 아님, 2026-11-14)이고 사건이 없을 때(OFF · S0)만 사람이 골라 차 토큰으로 부르며, 차 쪽(토큰 · 짝 상태 · 보낼 함 · ack)을 먼저 지운다. 성공 · 401 은 같은 처리이고, 네트워크 실패면 다시 보내지 않는다(중계의 짝은 아무도 읽지 못한 채 24시간 만료로 사라진다 — 운전자 교체, 2026-11-08 감사 하3). 워치도 동의 철회 때 워치 토큰으로 `pair/end` 를 부른다(워치 연결만 끊김).
- **휴대폰 철회의 `pair/end` 다시 시도(2026-11-08 · 감사 하2)** — 기기 저장을 바로 지우고 잡아 둔 토큰으로 마지막 sync 뒤 `pair/end` 를 부르는 순서는 그대로다. `pair/end` 가 실패하면(네트워크 · 5xx · 시간 초과) **그 토큰과 저장 시각만** 따로 남기고(이름 · 번호 · 위치 · 건강 값은 남기지 않음), 앱 화면 열림 · 서비스 시작 · sync 가 실패 뒤 다시 성공했을 때 다시 부른다. 성공하거나 401(이미 없는 짝)이면 지우고, 저장한 지 24시간(짝 만료)이 지나면 부르지 않고 지운다(그 정리도 다음 앱 화면 열림 · 서비스 시작 때 일어난다). 지금 짝의 토큰과 같은 토큰은 부르지 않는다(새 짝과 섞이지 않게). 로그에는 결과 종류(HTTP 상태 코드)만 남긴다.
- **워치 재시도(2026-11-08)** — 워치는 철회 때 자기 짝을 바로 지우고 그 워치 토큰만 「끝낼 토큰」으로 남긴다. `pair/end` 결과가 200 · 401 이 아니면(네트워크 · 시간 초과 · 5xx · 그 밖의 4xx) 남겨 두고 앱 실행 · 감시 시작 · 네트워크 복구 때 다시 부르며, 200 · 401 이면 지운다. 저장한 지 24시간이 지나면 부르지 않고 지운다. 새 짝의 토큰과 섞지 않는다.
- **기능 끄기는 짝을 유지한다**(PM 결정 2026-10-30 — 차가 켬 · 동의를 휴대폰 스냅숏에서 읽기 때문, §6.1). 꺼도 휴대폰은 sync 를 계속하고 `flow` 에 꺼짐(OFF) 설정 스냅숏을 싣는다. 짝은 24시간 만료로 사라진다.

## 4. 메시지

표기 — `T|null` 은 null 을 허용한다는 뜻이다.

- **필수 필드**는 `token` · `seq` · `sentAt` 과, 각 sync 의 주 상태(차 `vehicle`, 워치 직접 경로 `watch`)다. 빠지거나 형이 틀리면 400(토큰이 없으면 401).
- 중계가 정수로 검사하는 필드(`seq` · `sentAt` · 휴대폰 `responseAt`)는 **−2^63 이상 2^63 − 1 이하**(Kotlin `Long`)여야 하고, 밖이면 400 이다(2026-11-08 — 상대 앱이 응답 전체를 해석하지 못하는 것을 막는다). 음수는 막지 않는다. 지시 `ttlMs` 는 1 ~ 120,000 이다(2026-11-14 D-3 — 이전 1시간). `vehicle` · `watch` · `flow` 안쪽 수는 중계가 보지 않는다(§5).
- **선택 필드**(휴대폰 `watch` · `flow` · `commands` · `acks` · `carDisplay` · `healthConsent`, 지시의 `payload` · `to`)는 **생략하면 null(목록은 빈 목록, `payload` 는 `{}`, `to` 는 기본 대상)과 같게** 본다. 앱은 되도록 필드를 다 보내고 값을 모르면 null 을 보낸다.
- 문자열에 **짝 없는 서로게이트**(U+D800–DFFF 단독, `"\ud800"` 같은 이스케이프 포함)가 있거나, JSON 이 아닌 수 `NaN` · `Infinity` · `-Infinity`, 또는 범위를 넘어 무한이 되는 수(`1e999` · `-1e400` 등)가 있으면 400 이다. 중계 응답도 무한 · NaN 을 싣지 않는다(이중 방어).

### 4.1 sync 요청 · 응답

```jsonc
// CarSyncRequest
{"token":"<carToken>","seq":1761800000123,"sentAt":1761800000123,
 "vehicle":{...Vehicle},"flow":{...Flow}|null,"commands":[...Command],"acks":["<command id>"]}
// CarSyncResponse
{"serverTime":1761800000150,"peer":{...PhonePeer}|null,"watch":{...Watch + via · receivedAt · ageMs}|null,"commands":[...Command],

{"token":"<phoneToken>","seq":...,"sentAt":...,"watch":{...Watch}|null,
 "flow":{...Flow}|null,"commands":[...],"acks":[...],"responseAt":<int>|null,"carDisplay":{"hideHr":<bool>}|null,

// PhoneSyncResponse
{"serverTime":...,"peer":{...CarPeer}|null,"watch":{...Watch + via · receivedAt · ageMs}|null,"commands":[...],
```

| 필드 | 뜻 | 규칙 |
|---|---|---|
| `token` | 짝짓기에서 받은 그 역할의 토큰 | 틀리면 401 |
| `seq` | 보낸 쪽 상태 순번(정수) | 단조 증가. **앱을 다시 켜도 줄지 않게, 시작할 때 현재 에포크 밀리초에서 시작해 1씩 올린다**(권장). §5 참고 |
| `sentAt` | 보낸 기기 시각(ms) | 기록 · 표시용. 서버는 판단에 쓰지 않는다 |
| `vehicle` | 차 상태 | 차는 필수(객체) |
| `watch`(요청) | 휴대폰이 Data Layer 로 받은 최신 워치 상태 | 휴대폰은 객체 또는 null(워치가 직접 붙거나 연결이 없으면 null). 워치 직접 경로는 필수(객체) |
| `healthConsent` | 휴대폰에 지금 저장된 건강 관련 동의(휴대폰 요청만, 2026-11-08 추가 · 감사 하4) | bool · null · 생략(그 밖 400). 휴대폰은 sync 마다 싣는다. 생략 · null 은 옛 휴대폰 빌드로 보고 예전처럼 동작한다. `false` 면 중계는 워치 값을 보관 · 전달하지 않는다(§5 참고, §8). 차 `PhonePeer` 로는 내리지 않는다. 휴대폰 위치(`phoneLocation`)는 2026-11-08 요청에서 뺐다 — 옛 빌드가 실어 오면 중계가 형식만 검사하고 보관 · 전달하지 않는다(§5 · §8) |
| `flow` | 보낸 쪽이 들고 있는 상태 기계 스냅숏 | 객체 또는 null. 워치 요청에는 없음. **휴대폰은 짝지어진 동안 꺼짐(OFF)이어도 늘 싣는다**(§6.1 설정 전달) |
| `responseAt` | 휴대폰 화면 「괜찮아요」 응답 시각(휴대폰 요청만) | 정수 또는 null(응답 없음). 워치 `responseAt` 과 같은 규칙 — **휴대폰 벽시계(에포크 ms), 응답 순간 한 번만 정하고 sync 마다 다시 계산하지 않는다, 증가 표시 전용**(§4.3). 그 밖의 형은 400. 중계는 차가 받는 `PhonePeer` 에 그대로 싣는다(2026-10-30 추가 — 정차 중 휴대폰 화면 응답을 차의 상태 기계로 보낼 칸이 없었다) |
| `carDisplay` | 차 화면 표시 설정(휴대폰 요청만) `{"hideHr": bool}` | 객체 또는 null(2026-11-01 추가). `hideHr:true` 면 차 화면에 **심박 숫자와 맥박 신호 상태를 둘 다** 보이지 않는다(착용 · 갱신 같은 연결 사실은 보인다). 휴대폰 「차 화면에 심박 숨기기」 스위치 값이고 기본은 `false`(표시)다. 휴대폰은 짝지어진 동안 sync 마다 싣는다. 객체 · null 이 아니면 400. 중계는 안쪽을 보지 않고 휴대폰 상태와 함께 보관해 차가 받는 `PhonePeer.carDisplay` 로 그대로 싣는다. **차는 `peer` 가 null 이거나 `carDisplay` 가 없거나 null 이거나 `hideHr` 가 참거짓이 아니면 「모름」으로 보고 숨긴다**(G2 — 동승자 노출을 보수적으로). 흐름 상태와 관계없는 표시 설정이라 `flow.snapshot` 에 넣지 않는다(설계 `docs/design/car-spec.md` §9-3, PM 결정 2026-11-01) |
| `commands` | 상대에게 보낼 지시 | 한 번에 최대 32개. 워치 요청에서는 생략 가능 |
| `acks` | 내가 처리한 지시 id | 문자열 목록. 모르는 id 는 무시 |
| `serverTime` | 중계가 이 요청을 처리한 시각(ms) | |
| `peer` | 상대(차 ↔ 휴대폰)의 최신 상태 | 상대가 아직 한 번도 sync 하지 않았으면 null |
| `watch`(응답) | 중계가 고른 최신 워치 상태 + `via` · `receivedAt` · `ageMs` | §4.3. 차 · 휴대폰 응답 모두에 있다(PM 결정 — 차가 판정 주인이라 워치 직접 경로 값을 받아야 함). 워치 값이 없으면 null |
| `commands`(응답) | 나에게 와 있는 지시 | ack 전까지 매번 다시 온다. ttl 이 지나면 빠진다 |
| `watchDirectAgeMs`(응답) | 워치가 **직접 경로**(`/v1/watch/sync`)로 보낸 마지막 값의 나이(ms, 중계 시계 — `serverTime − 그 값의 receivedAt`) | 차 · 휴대폰 응답에만. 직접 값이 없으면(한 번도 안 붙음 · 워치 `pair/end` 뒤) null. 고른 `watch` 와 따로 낸다 — 고른 값은 더 최근 것만 싣기 때문에 직접 경로가 살아 있어도 `via:"PHONE"` 일 수 있다. 워치에 지시를 보낼 수 있는지는 이 값으로 판단한다(§4.3 「지시 가능 규칙」). 2026-10-30 추가, `:shared` 모델은 null 이면 싣지 않는 선택 필드 |

PhonePeer(차가 받음) · CarPeer(휴대폰이 받음)는 상대가 보낸 상태 그대로에 서버가 `receivedAt` 을 붙인 것이다.

```jsonc
// PhonePeer
{"seq":...,"sentAt":...,"receivedAt":<중계 시각>,"watch":{...Watch}|null,"flow":{...Flow}|null,
 "responseAt":<int>|null,"carDisplay":{"hideHr":<bool>}|null}
// CarPeer
{"seq":...,"sentAt":...,"receivedAt":<중계 시각>,"vehicle":{...Vehicle},"flow":{...Flow}|null}
```

`PhonePeer.watch` 는 휴대폰이 보낸 값 그대로(경유 값, null 가능)다. 상태 기계 입력으로는 **응답 최상위 `watch`(고른 값)** 를 쓴다.

**응답의 관용 해석(2026-11-08 · 코드 리뷰 하3)** — 받는 쪽은 응답의 `peer.watch` · 최상위 `watch`(차 · 휴대폰 응답 모두)가 객체가 아니거나 안쪽이 틀리면(모르는 enum · 빠진 필드 · 형이 다름) **그 필드만 「모름」(null)** 으로 두고 응답의 나머지는 그대로 읽는다(`:shared` `Watch.fromJsonOrNull`, `peer.flow` · `carDisplay` 와 같은 방식 — §4.6). 옛 중계가 보낸 `peer.phoneLocation` 은 맞든 틀리든 읽지 않고 넘긴다(2026-11-08 삭제, 감사 중4). 요청 쪽 검사(중계)는 그대로 엄격하다.

**휴대폰 화면 응답(2026-10-30 추가)** — 차는 sync 응답마다 `:shared` `ResponseChange(PHONE_SCREEN).onValue(peer.responseAt, 지금 단조)` 를 부르고(peer 가 null 이면 부르지 않음), 응답이 나오면 상태 기계에 넣는다. 규칙은 워치 `responseAt` 과 같다(§4.3 「받는 쪽은 증가만」). **정지 때만 유효** — 상태 기계는 정지가 아닐 때 `PHONE_SCREEN` 응답을 버린다(G5). 휴대폰이 주인이면 자기 화면 응답을 바로 자기 상태 기계에 넣는다.

사건 도중(OFF · S0 밖)의 첫 차량 입력은 **기어 P(확정 정지)만** 디바운스 없이 바로 정차 전이를 낸다(`VehicleState.confirmedStop`). 시동 꺼짐 · 속도만으로 본 정지는 5초 지켜본다. 2026-11-08 의 「주차 브레이크 체결도 즉시」는 뺐다.

- **고르는 규칙** — 워치 직접 상태(`/v1/watch/sync`)와 휴대폰 경유 상태(`/v1/phone/sync` 의 `watch`, null 이 아닐 때) 가운데 **중계가 더 늦게 받은 것(receivedAt)** 을 고르고 `via` · `receivedAt` · `ageMs` 를 붙인다. **받은 시각이 같으면 직접(`WATCH`)** 을 고른다. 휴대폰이 null 을 보내도 이전 직접 값은 남는다.
- **신선도 규칙** — 클라이언트는 **`ageMs` 가 30,000 을 넘으면 「워치 신호 없음」** 으로 본다(판정 · 화면 · 문자 모두). 중계는 마지막 값을 지우지 않고 계속 내려 주므로, 끊긴 워치의 오래된 `NORMAL` 을 정상으로 읽지 않게 하는 것은 이 규칙이다. 나이는 기기 시계와 섞지 않으려고 중계가 계산한다(`lastPulseAt` · `sentAt` 같은 기기 시각과 `serverTime` 을 빼지 않는다).
- 상태 기계 입력은 출처(직접 · 경유)와 무관하게 같다(PM 지시 2026-10-30).
- **지시 가능 규칙(2026-10-30 · PM 결정)** — 워치에 가는 지시(`ALERT_START` · `ALERT_STOP` · `TEST_SCENARIO` · `TEST_SCENARIO_STOP`)는 **워치가 중계에 직접 붙어 있을 때만** 닿는다. 「워치에 지시를 보낼 수 있다」는 **응답의 `watchDirectAgeMs` 가 null 이 아니고, 응답 뒤 지난 로컬 시간을 더한 값이 30,000 이하**일 때다(신선도 규칙과 같은 기준, `:shared` `WatchReach.canCommandWatch`). 고른 워치 값이 신선해도(Data Layer · 휴대폰 경유) 이 규칙이 거짓이면 워치에는 닿지 않는다. 휴대폰은 이때 테스트를 휴대폰 단독(LOCAL)으로 돌리고 「워치를 직접 연결하세요」를 보인다. 경보 지시는 그대로 보내도 된다(중계 큐에 남았다가 ttl 이 지나면 버려진다, §4.6).
- **응답 번호 규칙(2026-11-14 · B-5, `:shared` `WatchResponseTracker`)** — 워치 값에 `responseSeq` 가 있으면 번호로 본다: 처음 본 번호는 기준으로만, 기준(지금까지 본 가장 큰 번호)보다 **커지면** 응답 하나. 작은 번호 하나는 순서가 뒤바뀐 옛 값이라 무시하고, 작은 번호가 연달아 3번 오면 재설치로 보고 기준을 옮긴다(놓침이 거짓 응답보다 낫다, be-qa 3차). 작은 번호가 이어지는 동안은 그 연속의 첫 값을 임시 기준으로 두고 임시 기준보다 커지면 응답 하나와 함께 임시 기준을 올린다(재설치 직후 0 → 1 → 2 의 누름을 버리지 않게), 3번째에 기준 = 임시 기준. **남는 한계(PM 결정 20, 2026-11-14)** — 기준보다 낮은 옛 값 둘이 **커지는 순서로** 연달아 오면 임시 기준 규칙 때문에 응답 하나가 날 수 있고(예 10 → 5 → 6 이면 6 이 응답, `responses(10, 5, 6, 3, 4)` 는 6 하나가 응답 — 시험이 고정, be-qa 흔들기 34.8만 누름 가운데 6), 낮은 값이 3번 연달아 오면 기준이 그 임시 기준으로 내려간다. 재설치 직후 몇 초 안에 경보와 누름이 겹치면 첫 누름을 놓칠 수 있다. 워치가 번호의 세대(설치 · 저장 초기화마다 바뀌는 값)를 실으면 둘 다 닫히며, 제출 뒤 할 일로 남긴다. 한 번 번호를 본 뒤에는 `responseAt` 을 보지 않는다. 짝이 바뀌면 받는 쪽이 새로 잡는다. **차 · 휴대폰은 주인이든 아니든 받은 모든 워치 값으로 추적기를 부르고**, 나온 응답은 주인일 때만 상태 기계에 넣는다(주인일 때만 보면 다른 주인이 처리한 누름이 다음 내 경보에서 응답으로 읽힌다, be-qa 3차). 벽시계와 무관하다(앱2-하6). 경보 밖 누름은 워치가 번호를 올리지 않으므로 늦게 보여도 다음 경보를 끄지 않는다(app-wear 와 합의 — 받는 쪽 「경보 시작 때 기준점」은 받는 쪽이 그 전에 번호를 못 봤을 때 기준이 빈다). `responseSeq` 가 없으면 아래 `responseAt` 규칙이다.
- **워치 경보 맞추기(2026-11-14 · C-2, `:shared` `WatchAlertReconcile.step`)** — 주인(차 또는 휴대폰)은 sync 마다 자기 스냅숏의 경보 여부(`alerting` — 사고 `S5` 는 경보를 멈춘 상태)를 신선한 워치 값의 `alerting` 과 맞춘다.
  - 내가 경보 중인데 워치가 안 울리거나 · 단계(1 · 2)가 다르거나 · 다른 사건 id 로 울리면 **시작**을 다시 낸다(워치 대상만, 휴대폰 알람은 다시 내지 않음).
  - 내가 경보가 아닌데 워치가 울리면 **정지**를 다시 낸다 — 내 사건 id 면 바로, 모르는 사건 id(옛 지시 · 다른 주인)면 **그 id 를** 10초 지켜본 뒤(id 가 바뀌면 다시 셈). 정지에는 워치가 울리는 사건 id 를 싣는다.
  - 시작 · 정지 각각 10초에 한 번. 워치 값이 신선하지 않거나 옛 워치면 하지 않는다.
  - 워치는 정지한 사건 id 의 시작을 단계와 무관하게 모두 버리고(ack 만), 같은 사건 · 단계 · 강도가 울리는 중이면 다시 걸지 않으며, 사건 id 가 있는 정지는 지금 울리는 경보의 사건 id 가 같을 때만 듣는다. 사건 id 없는 지시는 지금 규칙이다.
- **받는 쪽은 `responseAt` 의 증가만 응답으로 본다**(2026-10-30 — 워치가 값을 sync 마다 다시 계산해 ±1ms 흔들려 흔들림만으로 경보가 꺼질 수 있었다, app-qa). `:shared` `ResponseChange` 규칙 — 처음 본 값은 기준으로만(앱 재시작 · 재짝짓기 뒤 옛 응답 무시), **기준보다 1,000ms(`MARGIN_MS`) 넘게 커질 때만** 새 응답, 같거나 작아지거나(벽시계가 뒤로 감) 여유 안의 변화는 무시, 기준은 마지막으로 본 값으로 옮긴다(null 은 기준을 바꾸지 않음). 워치 버튼은 `Response(WATCH_BUTTON)`, 휴대폰 화면은 `Response(PHONE_SCREEN)`(정지 때만). 값을 `serverTime` · 단조 시각과 빼지 않는다.
- 원신호(PPG · 가속도 원자료)는 워치 밖으로 보내지 않는다. 건강 관련 값은 위 다섯 가지(상태 코드 · 심박 정수 · 마지막 맥박 시각 · 착용 · 응답 시각)만 보낸다(G2 최소 수집).

### 4.4 Loc

Loc 은 **중계로 오가지 않는다**(2026-11-08 · 감사 중4 A 안 — `phoneLocation` 삭제). 휴대폰이 보호자 문자 · 119 작성 본문의 위치 줄을 만들 때와 차 내비 위치(`Vehicle.naviLat/Lon` · `naviAddress` 와 같은 뜻)를 다룰 때 쓰는 `:shared` 모델로 남는다.

| 필드 | 형 | 뜻 |
|---|---|---|
| `lat` · `lon` | number | WGS84 도 |
| `accuracyM` | number\|null | 수평 정확도(m) |
| `speedKmh` | number\|null | GPS 속도(km/h). 휴대폰이 자기 위치로 정지를 판단할 때 쓴다(§6) |
| `at` | int | 위치를 잡은 시각(ms, 휴대폰 시계) |
| `address` | string\|null | `Geocoder` 역지오코딩 결과 |

### 4.5 Flow

```json
{"state":"S1","since":1761800000000,"owner":"CAR","test":false,"snapshot":{}}
```

| 필드 | 뜻 |
|---|---|
| `state` | `OFF`·`S0`·`S1`·`S1R`·`AP`·`S2`·`S3`·`S4`·`S5`(설계 §4) |
| `since` | 이 상태에 들어간 시각(ms). §2 규칙 하나 — 보낸 쪽에 보정값이 있으면 **중계 시각**(`snapshot.clock:"SERVER"`), 없으면 보낸 기기 단조 시각(`"LOCAL"`), `:shared` `FlowStatus.forSync`. 받는 쪽은 `restoreLocal` 로 되돌린다(SERVER + 내 보정값 → 정확히, 다른 기기의 LOCAL · 내 보정값 없음 → 늦어지는 쪽으로 재기준) |
| `owner` | 지금 상태 기계를 돌리는 쪽 `CAR`·`PHONE` |
| `test` | 테스트 모드 흐름 — 워치 시나리오 세션(워치가 시뮬레이션 값을 내는 동안)만 참. 휴대폰 단독 시험은 거짓(§4.6 「차에서 테스트 요청」) |
| `localTest` | **선택 · 표시 전용**(2026-11-07). 휴대폰 단독(휴대폰 안) 시험이 도는 중이면 `true` 로 싣고, 아니면 생략한다(생략 = `false`, `Watch.noSignal` 방식). 휴대폰 sync 에만 있다. 받는 쪽(차)은 상태 기계 입력으로 쓰지 않는다 — 판정 · 경보 · 문자에 영향이 없고, 차의 시작 요청을 풀고 정차 화면 안내 한 줄에만 쓴다. 옛 판은 모르는 필드라 무시한다(`:shared` `FlowStatus.localTest`) |
| `smsDone` | **선택 · 휴대폰 흐름만**(2026-11-14, 합동 점검 A-1). 보호자 문자 결과 `[{"eventId":"event-…","kind":"EVENT"·"CANCEL"·"ACCIDENT"·"OBSERVE","done":"SENT"·"NOT_SENT"·"PENDING"}]`. **확인의 원본은 휴대폰 문자 기록**이고 중계 ack 는 확인이 아니다(건너뛴 경우에도 ack 가 나감). 범위는 지금 짝에서 생긴 실제 사건 가운데 미해결이거나 끝난 지 10분 안인 것 전부(테스트 제외, `:shared` `SmsDone.select`). 보냄 · 확인 못 함은 `SENT`. `NOT_SENT` 는 「보내지 않음」 기록이 남는 경우다 — 휴대폰 방어(참여 전 · 묵은 사건)나 원격 문자 상한에 막힌 문자, 보내지 않은 취소(같은 사건 · 사건 문자 없음 · 실패). 결과를 기다리거나 다시 보내는 중이면 `PENDING`. **동의 · 보호자 번호가 없을 때와 사건 · 사고 문자의 최종 실패는 기록이 남지 않아 `smsDone` 에 실리지 않는다** — 차 보낼 함은 그 문자를 상한(사건이 끝난 뒤 10분)까지 다시 싣는다. 번호 · 본문 · 위치는 싣지 않는다(G2). 생략 = 싣지 않음(차 · 옛 휴대폰), 빈 배열 = 확인된 것 없음. 틀린 항목은 그 항목만 버린다. 옛 판은 무시한다 |
| `snapshot` | 주인을 넘길 때 그대로 이어 가는 데 필요한 타이머 · 보낸 문자 표시 · 119 작성 연 표시 · **사건 id 문자열** 등. 내용은 `:shared` flow(`SnapshotCodec`)가 정하고, `"clock":"SERVER"` 이면 모든 시각이 중계 시각이다. 사건 id 는 넘김 때 바꾸지 않는다. 중계는 들여다보지 않는다 |

### 4.6 Command

```json
{"id":"7d4f0a9e-2f3b-4c55-9d62-0f1e6a1b2c3d","type":"ALERT_START","payload":{},
 "ttlMs":30000,"test":false,"from":"CAR","to":"WATCH"}
```

| 필드 | 규칙 |
|---|---|
| `id` | 보낸 쪽이 만드는 UUID 문자열(1~64자, 65자부터 400). 같은 id 는 그 지시의 ttl 동안 받는 쪽마다 한 번만 큐에 들어간다(재전송 안전). 중복 막기 기록은 ttl 이 지나면 지우므로, ttl 이 지난 뒤 같은 id 를 보내면 새 지시로 받는다 — id 는 지시마다 새로 만든다 |
| `type` | 아래 12가지(2026-11-01 `TEST_REQUEST` 추가). 그 밖은 400 |
| `payload` | 객체(생략하면 `{}`). 중계는 들여다보지 않는다 |
| `ttlMs` | 1 ~ 120,000(120초, 2026-11-14 D-3 — 이전 1시간). 중계가 받은 시각부터 센다. 지나면 큐에서 버린다. 지시 하나(JSON)는 **8KB 이하**, 받는 쪽마다 중복 막기 기록(지시 id)은 **512개까지**(넘으면 먼저 만료될 것부터 버림) |
| `test` | 테스트 모드 지시. 받는 쪽은 테스트 표시를 화면 · 문자에 싣는다 |
| `from` | 보낸 역할 `CAR`·`PHONE`·`WATCH`. **요청 경로의 역할과 같아야** 한다(다르면 400) |
| `to` | `PHONE`·`CAR`·`WATCH`·`ALL`(선택, 대문자 그대로). 생략 · null 이면 차 → `PHONE`, 휴대폰 → `CAR`, 워치 → `PHONE`. 그 밖의 값(`""` · `0` · `false` · 소문자 등)과 자기 자신은 400. `ALL` 은 보낸 쪽을 뺀 나머지 모두. 응답에서는 늘 채워서(없었으면 기본값) 내려간다 |

- 받는 쪽은 처리(또는 무시하기로 결정)한 뒤 다음 sync 의 `acks` 에 id 를 넣는다. ack 는 받는 쪽 큐에서만 지운다(`ALL` 은 쪽마다 따로 ack).
- 큐는 쪽마다 최대 256개, 넘치면(257번째) 오래된 것부터 버린다.
- 지시는 「한 번 이상」 전달된다. 받는 쪽은 처리한 id 를 기억해 두 번 실행하지 않는다.
- **받는 쪽은 모르는 type(또는 형식이 틀린 지시)을 그 지시만 건너뛰고 「지원하지 않음」으로 ack 한다**(2026-10-30 · PM 결정 — 앱 빌드가 섞여도 지시 하나 때문에 응답 전체를 못 읽지 않게). 나머지 지시 · `peer` · `watch` 는 그대로 처리한다. `:shared` 응답 모델의 `skippedCommandIds` 가 건너뛴 id 목록이다(id 가 문자열이 아니면 ack 할 수 없어 버린다). 보내는 쪽 검사는 그대로다 — 중계는 모르는 type 을 400 으로 거른다.
- **관용 해석 목록**(그 필드만 null, 응답 전체는 읽음) — `peer.flow` · `peer.carDisplay` · `peer.watch` · 최상위 `watch`(뒤 둘은 2026-11-08 추가, §4.1) · 형식이 틀린 지시(그 지시만 건너뜀). 옛 `peer.phoneLocation` 은 아예 읽지 않는다(2026-11-08 삭제).
- **상대 `peer.flow` 가 읽히지 않으면 그 필드만 「모름」(null)** 으로 두고 `peer` 의 나머지(`vehicle` · `watch` · `carDisplay` · `responseAt`) · 최상위 `watch` · `commands` 는 그대로 읽는다(2026-11-02 · 리뷰 중 7 — 모르는 enum · 빠진 필드가 든 흐름 하나 때문에 응답 전체를 버리지 않게, `:shared` `FlowStatus.fromJsonOrNull`). 또 중계가 2xx 를 주었는데 받는 쪽이 본문을 못 읽어도 **링크는 살아 있는 것**으로 본다(차는 주인을 내려놓지 않고 마지막 성공 시각을 갱신, 상태 입력만 없음).
- **버린 지시는 다시 보내지 않는다**(설계 의도). ttl 이 지났거나 큐가 넘쳐 버린 지시는 중계가 되살리지 않고 보낸 쪽에 알리지도 않는다. 오래된 경보 지시가 늦게 실행되는 것을 막으려는 것이다. 여전히 필요하면 주인이 지금 상태로 **새 id 의 지시**를 다시 낸다.

#### 지시 허용 표(2026-11-14 · 합동 점검 D-1)

보낸 역할마다 type 별로 받을 수 있는 쪽은 **공용 표 `contracts/guardian/command-roles.json` 하나**다(중계 `COMMAND_ROLES` · 통합 `FakeRelay` 가 이 파일과 시험으로 대조된다). `to` 를 생략하면 기본 대상까지 풀어서 본다. 표 밖 지시가 하나라도 있으면 **그 sync 전체가 400**(상태도 덮지 않는다). `TEST_REQUEST` · `TEST_SCENARIO` · `TEST_SCENARIO_STOP` 은 `test:true` 만 받는다. **워치는 지시를 내지 않는다.** `CAR → PHONE FLOW_SNAPSHOT` 은 표에 없다(차는 이 지시를 내지 않는다 — 넘김은 휴대폰 → 차만).

| 보냄 | type → 받는 쪽 |
|---|---|
| CAR | `ALERT_START` → WATCH · PHONE, `ALERT_STOP` → ALL · WATCH · PHONE, `SHOW` · `OPEN_119_COMPOSE` · `SEND_GUARDIAN_SMS` · `TEST_REQUEST` → PHONE |
| PHONE | `ALERT_START` → WATCH, `ALERT_STOP` → ALL · WATCH · CAR, `SPEAK` · `SHOW` · `AMBIENT` · `OPEN_SEARCH` · `FLOW_SNAPSHOT` → CAR, `TEST_SCENARIO` · `TEST_SCENARIO_STOP` → WATCH |
| WATCH | 없음 |

#### 지시 종류별 payload

payload 는 `:shared` `protocol/Payloads.kt`(`Payload.*` · `DirectiveCommands`)가 만들고 읽는다. 아래 표는 그 코드와 글자까지 맞춘 것이다(PM 채택 2026-10-30). 문구는 `:shared` `text/Texts.kt` 문구 표에서 오고 G1(「실신」 등 판정어 금지)을 따른다. 중계는 payload 를 들여다보거나 판정하지 않는다. 예외는 하나, `AMBIENT` 의 `mode:"BLUE_RED_BLINK"` 거부(이중 방어, 아래 표 · §7)다.

| type | 보냄 → 받음 | payload 예 | 지킬 것 |
|---|---|---|---|
| `ALERT_START` | 주인 → WATCH(진동 · 소리) · PHONE(알람) | 워치 경보 1 `{"stage":"S1","level":1,"vibrate":true,"sound":false,"maxVolume":false,"durationMs":15000}` · 휴대폰 경보 2 `{"stage":"AP","level":2,"vibrate":false,"sound":true,"maxVolume":true,"durationMs":20000}` | `stage` 는 Flow `state` 값. 휴대폰은 `USAGE_ALARM` 최대, 끝나면 음량 복원. **`durationMs` 는 단계 표시용이다 — 기기는 이 시간이 지나도 경보를 스스로 끄지 않고 `ALERT_STOP` 이 올 때까지 계속한다**(PM 결정 2026-10-30, 설계 §14). `eventId`(선택, 2026-11-14 · C-2)는 이 경보의 사건 id 다(상태 기계 `facts.eventId`). 없으면 받는 쪽은 지금 규칙 |
| `ALERT_STOP` | 주인 → ALL | `{"reason":"CLEARED","eventId":"event-1761800000000"}` | 보내는 값은 `CLEARED` 하나다. 받는 쪽 모델(`AlertStopReason`)은 `RESPONDED` · `PAIR_END` 도 읽는다. `eventId`(선택, 2026-11-14)는 멈추는 경보의 사건 id — **사고(S5)로 바뀔 때 내는 정지에는 옛 사건 id** 를 싣는다(새 사고 id 를 실으면 워치가 옛 경보를 못 끈다, app-qa) |
| `SPEAK` | 주인 → CAR | `{"text":"응답 확인이 필요합니다. 안전한 곳에 차를 세우세요.","lang":"ko-KR"}` | 차는 Pleos TTS, 오디오 포커스 `GAIN_TRANSIENT`. `lang` 이 없으면 `ko-KR` |
| `SHOW` | 주인 → CAR(「워치 착용 확인」 · 「워치 신호 없음」 은 CAR · PHONE 각각) | 주행 중 `{"line":"응답 확인 필요 · 워치 버튼을 누르세요","button":null}` · 정지 때 `{"line":"쉬는 중 · 괜찮아지면 다시 출발하세요","button":"괜찮아요"}` | 주행 중 한 줄 · 버튼 없음, 정지 화면(AP · S2 · S4)만 버튼 하나(G5) |
| `AMBIENT` | 주인 → CAR | 켤 때 `{"on":true,"mode":"INTERIOR_ALERT"}` · `{"on":true,"mode":"PARKED_RESCUE"}`, 끌 때 `{"on":false,"mode":null}` | `mode` 는 `INTERIOR_ALERT`(주행 중 호박색 한 번) · `PARKED_RESCUE`(정차 뒤 S2 · S4 백색) · `BLUE_RED_BLINK`. **`BLUE_RED_BLINK` 는 법률 검토 전 금지(G6) — 중계도 거부**한다. `:shared` 상태 기계는 내지 않고 payload 모델도 만들지 못하게 막으며, 그래도 오면 중계가 그 sync 요청 전체를 400 으로 거른다(대소문자 무시 — `blue_red_blink` 등도 거부, 같은 요청의 다른 지시도 큐에 넣지 않고 상태도 덮지 않음, PM 결정 2026-10-30). 켤 때만 `mode`, 끌 때 `mode:null` |
| `OPEN_SEARCH` | 주인 → CAR | `{"query":"응급실"}` | 정지 뒤(S4)에만 내비 검색 화면 |

#### 차에서 테스트 요청(2026-11-01 · PM 결정)

이유 — 차 화면에서 정차 중 테스트를 시작 · 멈출 수 있게 하되, 테스트 모드는 휴대폰에서만 바꾸고(§6.1) 워치 지시 경로는 하나(직접 경로, §4.3)로 지킨다. 보호자 테스트 문자 확인(P17)과 119 미리보기(P18)는 휴대폰에만 있다(G4).

- 차는 `TEST_REQUEST` 를 휴대폰에 보낸다(`from:"CAR"` · `test:true`). 다른 쪽(`PHONE` · `WATCH`)에서 온 `TEST_REQUEST` 는 휴대폰이 실행하지 않고 ack 한다.
- **`START`** — 휴대폰은 홈 「테스트 시작」(P15)과 같은 길 · 같은 검사로 시작한다. 검사는 기능 켬 · 등록 · 동의 3종(준비), 이동 판단이 정차(또는 「모름」 + 「정차 중입니다」 확인), 사건 없음(흐름 `OFF` · `S0`), 진행 중인 테스트 없음이다. 워치 지시 가능 규칙(§4.3)이 참이면 워치 시나리오(`TEST_SCENARIO`), 아니면 휴대폰 단독 + 「워치를 직접 연결하세요」 안내다. 시나리오는 `PULSE_LOST` 다. 시나리오 길이는 홈 테스트와 같은 휴대폰 값 120초(`LocalTestRun.DURATION_MS`)이고 `durationMs` 120000 과 같다 — 이미 검증된 경보 흐름(정상 → 경보 1 · 2 → 무응답)을 그대로 쓴다. 차 확인 창에는 약 2분으로 표시한다(PM 결정 2026-11-01).
- **`STOP`** — 휴대폰 「테스트 멈추기」와 같다(워치 시나리오였으면 `TEST_SCENARIO_STOP`). 진행 중인 테스트가 없으면 아무것도 하지 않는다. 휴대폰에서 시작한 테스트도 멈춘다.
- **거부는 따로 답하지 않는다.** 시작할 수 없으면(주행 중 · 사건 중 · 준비 안 됨 · 이미 테스트 중) 휴대폰은 ack 만 하고 테스트를 켜지 않는다. 결과 지시 · 새 필드는 없다(가장 단순한 길).
- **차는 결과를 기존 상태로 판단한다** — 휴대폰 sync 의 `flow.test`(차가 주인이면 휴대폰 설정 스냅숏의 `test`, §6.1)가 참이 되면 시작된 것이다. 요청을 보낸 뒤 **15초 안에** 참이 되지 않으면 「휴대폰이 답하지 않습니다 · 휴대폰 앱을 확인하세요」를 보이고 버튼을 되살린다(설계 car-spec §5). 멈춤도 같다 — `flow.test` 가 거짓이 되면 멈춘 것이다. ack 는 「받았다」만 뜻하고 시작 여부를 뜻하지 않는다.
  - **휴대폰 단독(휴대폰 안) 시험은 `flow.test` 에 싣지 않고 `flow.localTest:true`(§4.5, 표시 전용)로 알린다**(2026-11-07 · PM 결정, 휴대폰 시험 `RealIncidentDuringLocalTestTest` · 차 시험 `CarHubDisplayTest` · 통합 `CarTestRequestTest`). 휴대폰 안 시뮬레이션은 휴대폰 밖으로 아무 신호도 내지 않으므로, 그동안 차가 받는 실제 워치 값은 실제이고 차의 흐름 · 문자 지시도 실제여야 한다. `flow.test` 가 참이 되는 것은 워치 시나리오(`TEST_SCENARIO`) 세션뿐이다. 차는 `localTest` 가 참이면 시작 요청을 **답한 것으로 풀고**(「휴대폰이 답하지 않습니다」를 내지 않음) 정차 화면 테스트 입구에 「휴대폰에서 테스트 중 · 차 화면은 실제 상태입니다」를 두며, 그동안 새 시작 요청은 보내지 않는다(흐림). 주행 중 화면 · 경보 화면에는 두지 않는다(G5). 거짓이 되면 안내도 사라진다. 휴대폰이 정말 답하지 않으면(둘 다 거짓) 15초 규칙은 그대로다.
- 「모름」과 차 판단 — 차 링크가 살아 있으면(`serverTime − peer.receivedAt` ≤ 10초) 휴대폰의 이동 판단은 늘 차 값(주행 · 정차)이고 「모름」이 되지 않는다. 그래서 차가 정차 중에 보낸 `START` 는 휴대폰에서도 정차로 통과한다. 휴대폰이 「모름」인데 `START` 가 왔다면 차 링크가 끊긴(오래된) 지시이므로 차의 정차 보장을 믿지 않고 「정차 중입니다」 확인이 있을 때만 시작한다.
- **세션이 끝나는 때(2026-11-07)** — 멈춤 요청 외에, 시나리오 120초가 지났고 그 테스트의 흐름이 경보 중(`S1` · `AP` · `S3` · `S4`)이 아니면 휴대폰이 바로 끝낸다. 경보 중이면 벗어난 다음 틱에 끝낸다. 차 flow 를 모르면 단정하지 않는다. 시작 뒤 7분(120초 + 300초)은 마지막 안전장치다. 세션이 끝나 표시가 거짓이 되면 상태 기계는 테스트 사건의 `S1R` · `S2` 에서도 표시를 끄고 재경보 단계를 버린 채 `S0` 으로 돌아간다. 켜기는 여전히 `OFF` · `S0` 에서만 받고, 경보 중에는 켜기 · 끄기 모두 받지 않는다.
- **테스트 흐름 거두기(2026-11-14 · 합동 점검 B-7)** — 표시 끄기와 따로, 상태 기계 입력 `FlowInput.WithdrawTest` 는 **흐름이 테스트(`test:true`)일 때만** 경보 중(`S1` · `AP` · `S3` · `S4`)과 응답 뒤(`S1R` · `S2`)에서 경보를 멈추고(`ALERT_STOP`, test 표시) 재경보 단계를 버린 채 `S0` 으로 간다. **실제 흐름과 `S5`(늘 실제)는 어떤 경우에도 거두지 않는다.** 거두지 않은 테스트 사건이 그 뒤 실제 사건을 막지 않게 하려는 것이다. 판정 주인이 세션이 정말 끝났을 때(위 세션 끝 규칙 · 7분 안전장치) 한 번 넣는다 — 차가 주인이면 차가 휴대폰 설정 스냅숏의 `test` 가 거짓이 된 것을 보고 넣는다. 매 주기 넣는 표시 끄기(`TestMode(false)`)는 워치 값이 잠깐 없을 때도 거짓이라 거두기로 쓰지 않는다. 앱이 이 입력을 넣는 일은 다음 묶음이다(그 전에는 지금 동작 그대로).

#### 에어백 사고는 늘 실제(2026-10-30 · PM 결정)

이유 — 테스트 시나리오는 워치 신호만 흉내 내고 에어백은 흉내 내지 않는다. 에어백 전개는 차의 실제 하드웨어 사실이라, 테스트 중이었다는 이유로 실제 사고를 `[테스트]` 문자 · 119 미리보기로 처리하면 안 된다(app-qa 차 앱 2차 검증 권고).

- 상태 기계(`:shared` `FlowMachine`)는 에어백 전개를 받으면 테스트 모드와 상관없이 S5 로 가고, 그 사고의 모든 지시(`SEND_GUARDIAN_SMS` kind `ACCIDENT` · `SPEAK` · `SHOW` 등)는 `test:false` 다.
- 테스트 사건(S1 ~ S4 · S1R · S2) 도중이면 먼저 그 테스트 사건을 정리한다 — 경보가 울리고 있으면 `ALERT_STOP`, 실내 조명이 켜져 있으면 끄는 `AMBIENT`(둘 다 `test:true`). S1R · S2 처럼 경보가 이미 멈춘 상태에서는 `ALERT_STOP` 이 나가지 않는다. 그다음 테스트 사건의 사실은 버린 채 **새 실제 사고**(새 `eventId` `accident-…`, `firstAlertAt` · `noResponseAt` 없음)를 연다. 테스트 사건의 취소 문자는 내지 않는다.
- 테스트 표시는 그 실제 사고(S5)가 끝날 때까지 다시 켜지지 않는다(테스트 모드 요청은 OFF · S0 에서만 받는다). 사고가 끝나 S0 으로 돌아오면 휴대폰 설정대로 다시 켤 수 있다.
- 휴대폰은 테스트를 끝낼 때 워치 테스트(WATCH 표시)였으면 `TEST_SCENARIO_STOP` 을 워치에 보낸다(워치 시뮬레이션 값의 `test:true` 가 실제 사고 흐름에 섞이지 않게, 2026-10-30).
- **휴대폰은 테스트 진행 중이어도 `SEND_GUARDIAN_SMS` kind `ACCIDENT` · `test:false` 를 막지 않는다**(실제 사고). 「테스트 중에는 테스트 표시 없는 문자를 막는」 이중 방어는 `ACCIDENT` 를 뺀 kind(`EVENT` · `CANCEL` · `OBSERVE`)에만 둔다.

#### 문자 지시는 사실만(2026-10-30 · PM 결정)

등록 정보(운전자 이름 · 생년월일 · 보호자 이름 · 번호 · 차 번호 · 색)는 **휴대폰에만** 있다. 그래서 주인이 차든 휴대폰이든 `SEND_GUARDIAN_SMS` · `OPEN_119_COMPOSE` 에는 사건 사실만 싣고, 본문은 휴대폰이 만든다. 개인정보가 중계 · 차를 거치지 않는다(G2 최소 수집). 이유 — 차가 주인일 때 차는 본문을 못 만들어 두 지시가 빠졌다(app-android 보고).

| 사실 필드 | 형 | 뜻 |
|---|---|---|
| `clock` | `"SERVER"`·`"LOCAL"` | 아래 시각의 기준. 보낸 쪽에 시계 보정값이 있으면 `SERVER`(중계 시각), 없으면 `LOCAL`(보낸 기기 단조 시각) — 넘김 스냅숏과 같은 규칙(§2 · §6) |
| `firstAlertAt` · `stoppedAt` · `noResponseAt` · `responseAt` · `accidentAt` | int\|null | 첫 경보 · 정차 · 무응답 · 응답 · 사고(에어백) 시각 |
| `carStateMissing` | bool | 휴대폰이 주인이라 차 상태 없이 판정함 |
| `test` | bool | 테스트 사건(지시의 `test` 와 같음). 본문에 `[테스트]` |

- 받는 쪽은 `:shared` `WireFacts.toLocal` 로 자기 단조 시각으로 되돌린다. `SERVER` + 내 보정값 → 정확히. `LOCAL` 이고 내가 나에게 낸 지시 → 그대로. 그 밖(내 보정값 없음 · 다른 기기의 `LOCAL`) → 가장 늦은 시각을 지금에 맞춘 근사(「시계 미확인」).
- 휴대폰은 본문을 사실 + 등록 정보(로컬) + 차 상태(phone/sync 응답 `peer.vehicle`, 끊겼으면 없음) + 고른 워치 값(30초 넘으면 워치 줄 없음) + 휴대폰 위치(없으면 차 내비 위치) + 동의 3종으로 만든다(`IncidentComposer`). 보호자 미등록이면 만들지 않고 등록 화면으로 보낸다(`GUARDIAN_MISSING`).
- **휴대폰이 주인일 때도 같은 지시를 같은 함수로 처리한다.** 받는 쪽이 자기 자신(`PHONE`)인 지시는 중계로 보내지 않고(중계는 `to` 가 자기 자신이면 400) 바로 처리한다(`DirectiveCommands.splitLocal`).

### 4.7 워치 ↔ 휴대폰 Data Layer(2026-10-30 추가 — 휴대폰 · 워치 앱 구현을 계약으로 고정)

| 항목 | 값(`:shared` `protocol.DataLayer`) | 뜻 |
|---|---|---|
| MessageClient 경로 | `/guardian/watch`(`PATH_WATCH`) | 워치 → 휴대폰. 본문은 Watch JSON(§4.3, UTF-8 — `Watch.toJson`), 약 1초마다(`WATCH_INTERVAL_MS`). 선택 경로 — 워치가 중계에 직접 붙으면(`/v1/watch/sync`) 쓰지 않아도 된다 |
| capability(워치) | `guardian_watch`(`CAPABILITY_WATCH`) | 워치 앱이 광고. 휴대폰이 받을 노드를 고를 때 |
| capability(휴대폰) | `guardian_phone`(`CAPABILITY_PHONE`) | 휴대폰 앱이 광고. 워치가 보낼 노드를 고를 때 |

- **휴대폰 → 워치 Data Layer 지시는 없다.** 워치가 받을 지시(`ALERT_START` · `ALERT_STOP` · `TEST_SCENARIO` · `TEST_SCENARIO_STOP`)는 중계 `to:WATCH`(또는 `ALL`)로만 가고, **워치가 중계에 직접 붙어 있을 때만 받는다**(PM 결정 2026-10-30 — 경로를 하나로 둔다. 시험 휴대폰 Note10 은 Watch9 와 짝이 안 돼 직접 경로가 유일하다). Data Layer 는 워치 → 휴대폰 상태 데이터만 나르는 보조 경로다.
- 그래서 휴대폰은 Data Layer 로 받은 워치 값만으로 「워치에 지시를 보낼 수 있다」고 보지 않는다. 판단은 §4.3 지시 가능 규칙(`watchDirectAgeMs`)으로 한다.
- 휴대폰은 받은 워치 값을 phone/sync 의 `watch` 로 싣는다(건강 관련 동의가 있을 때만, §8).

## 5. 중계의 상태 보관 규칙

- 쪽(차 · 휴대폰 · 워치 직접)마다 **최신 상태 1건만** 보관하고 덮어쓴다.
- `seq` 가 그 쪽의 이전 `seq` 보다 **1 ~ 1,000 작으면 상태를 덮지 않는다**(늦게 도착한 옛 요청). 같으면 덮는다(같은 요청 재전송). 이때도 응답은 정상(200)으로 주고, 함께 온 `commands` · `acks` 는 처리한다(지시는 id 로 중복을 막는다).
- **seq 재시작(2026-11-08 — 공통 하5)** — 같은 토큰에서 `seq` 가 이전보다 **1,000 넘게 작으면** 앱이 다시 켜졌고 기기 시계가 뒤로 간 것으로 보고 **덮는다**. 그 seq 가 새 기준이 된다(그 뒤로는 다시 위 규칙). 근거 — sync 는 2초마다 seq 를 1씩 올리므로 늦게 도착하는 요청의 차이는 수십을 넘지 않는다. 남는 틈 — 재시작 시각이 시계가 뒤로 간 폭과 1초 안쪽으로 겹쳐 차이가 1 ~ 1,000 이면 그 쪽 상태가 최대 1,000번 sync(약 33분) 동안 덮이지 않는다. 또 재시작 직후 옛 프로세스의 요청이 늦게 오면 한 번 덮일 수 있고, 다음 sync 가 다시 덮는다.
- 새 코드로 다시 참여한 역할(§3.1)은 seq 기준을 비워, 새 토큰의 첫 sync 는 seq 와 관계없이 덮는다.
- 그래도 **`seq` 는 시작 시 에포크 밀리초에서 시작**한다(권장 유지). 0 부터 다시 세면 이전 값과의 차이가 커서 재시작으로 받아들여지긴 하지만, 같은 실행 안에서 줄지 않는 것이 전제다.
- `receivedAt` 은 중계 시각이다. 중계는 받은 순간을 단조 시계로 보관하고, 응답마다 `serverTime − 경과` 로 바꿔 싣는다(§2).
- 중계는 `vehicle` · `watch` · `flow` · `payload` 안쪽 필드를 검사하지 않는다(겉 형만 본다). 예외는 `AMBIENT` 의 `mode:"BLUE_RED_BLINK"` 거부 하나다(§4.6).
- 휴대폰 `responseAt` 은 휴대폰 상태와 함께 보관하고(생략하면 null) 차가 받는 `PhonePeer` 에만 싣는다.
- 휴대폰 `carDisplay` 도 같다(2026-11-01) — 최신 1건을 휴대폰 상태와 함께 메모리에 두고(생략하면 null) 차가 받는 `PhonePeer` 에만 싣는다. seq 가 줄어 상태를 덮지 않으면 `carDisplay` 도 덮지 않는다.
- **휴대폰 위치는 보관하지 않는다(2026-11-08 — 보안 감사 중4, A 안)** — 휴대폰 sync 에 `phoneLocation` 이 와도 옛 휴대폰 빌드 호환으로 형식(객체 또는 null)만 검사하고(틀리면 400), 휴대폰 상태에 저장하지 않는다. 그래서 차가 받는 `PhonePeer` 에는 `phoneLocation` 키 자체가 없다. 근거 — 차는 이 값을 읽지 않고, 휴대폰 문자 본문은 휴대폰 자신의 위치로 만든다(G2 최소 전송).
- **건강 동의가 꺼지면 워치 값을 보관하지 않는다(2026-11-08 — 보안 감사 하4)** — 휴대폰 sync 의 선택 필드 `healthConsent`(bool 또는 null, 그 밖의 형은 400)를 짝마다 **가장 최근 1건** 보관한다. seq 가 줄어 휴대폰 상태를 덮지 않는 요청은 이 값도 바꾸지 않는다. 휴대폰 상태와 달리 차 `PhonePeer` 로 넘기지 않는다.
  - 값이 `false` 면 ① 그 요청을 받는 순간 이미 보관한 워치 직접 값을 지우고 ② 그 뒤 워치 직접 sync 의 `watch` 를 보관하지 않으며(응답은 그대로 200) ③ 휴대폰이 `watch` 를 실어 보내도 보관하지 않는다. 그래서 차 · 휴대폰 응답의 최상위 `watch` 와 `peer.watch` 는 null 이다. 워치 직접 sync 를 받은 시각은 남겨 `watchDirectAgeMs`(§4.3 지시 가능 규칙)는 그대로 계산한다.
  - `true` 이거나 생략 · null(옛 휴대폰 빌드)이면 지금과 같다. `false` → `true` 로 바뀌어도 지운 값은 되살아나지 않고, 그 뒤 새로 온 워치 값부터 다시 내려간다.
- `watchDirectAgeMs` 는 보관한 워치 직접 상태의 `receivedAt` 으로 응답마다 계산한다(따로 보관하지 않음). 워치 `pair/end` 로 직접 상태가 지워지면 null 이다.
- 형식 검사는 상태 · 큐를 바꾸기 전에 한다. 400 을 받은 요청은 상태도 덮지 않고 그 안의 어떤 지시도 큐에 넣지 않는다. 안쪽 규격 검사는 `:shared` 직렬화 시험이 맡는다.

## 6. 판정 주인

- **차 앱의 마지막 sync 가 10초 안이고 차가 흐름에 스스로 주인이라고 실었을 때(`flow.owner == "CAR"`) 차가 상태 기계 주인**이다(사용자 정정 「허브 = Pleos 앱」, 2026-11-14 합동 점검 A-4 — 차가 내려놓았으면(`owner:"PHONE"`) 신선해도 휴대폰이 주인, `:shared` `Ownership.decide` 세 인자판). 넘겨받기 세부는 §6.4.
- 휴대폰은 `serverTime - peer.receivedAt`(둘 다 중계 시계)으로 차의 신선도를 잰다. 10,000ms 를 넘거나 `peer` 가 null 이면 **휴대폰이 대신 주인**이 되고 「차 상태 없음」을 표시 · 문자에 적는다. 정지 판정은 **휴대폰 자신의 위치(로컬) GPS 속도**로 대신한다 — 10초 안에 잡은 위치의 거르기 전 속도를 상태 기계 정지 기준으로 판단한다(`PhoneEngine.stopped` · `gpsSpeed`). 중계를 거치지 않는다(2026-11-08, `phoneLocation` 삭제).
- 차는 자기 sync 가 성공한 마지막 시각(차 시계)으로 링크를 잰다. 10초 넘게 실패하면 휴대폰이 주인이 됐다고 보고 차 안 경보(TTS · 화면)는 계속하되 상대에게 낼 지시는 쌓지 않는다 [추정 — `:shared` 와 확정].
- 주인을 넘길 때 상태 · 타이머는 그대로 넘긴다. 각자 sync 에 `flow`(snapshot 포함, §2 규칙 하나 — `forSync`)를 싣고, 새 주인은 상대 `peer.flow` 를 `restoreLocal` 해 이어 간다. 즉시 알려야 하면 `FLOW_SNAPSHOT` 지시를 쓴다. 넘김용 스냅숏의 시각은 보낸 쪽이 자기 시계 보정값(`offset = serverTime − 단조 왕복 중간값`, 최근 60초 표본 중 왕복 최단 · 왕복 5초 초과 무시)으로 **중계 시각**으로 바꿔 싣고(`clock:"SERVER"`), 받는 쪽은 자기 보정값으로 단조 시각으로 되돌린다. 받는 쪽에 보정값이 없으면 타이머가 늦어지는 쪽으로만 재기준한다(앞당기지 않음). 사건 id 는 바꾸지 않는다.
- 워치는 주인이 되지 않는다. 판정 입력(`verdict`)만 준다.

### 6.1 설정 전달(2026-10-30 문서화 — 차 앱 구현을 계약으로 고정)

- 켬 · 동의 3종(긴급 연락 정보 · 건강 관련 · 위치 제공) · 테스트 모드는 **휴대폰에서만** 바꾼다. 차 앱은 이것을 휴대폰 sync 의 `flow` 스냅숏(`snapshot.powerOn` · `snapshot.consents` · `snapshot.test`)에서 읽어 자기 상태 기계에 넣는다. `snapshot.test` 는 워치 시나리오 세션(워치가 시뮬레이션 값을 내는 동안)만 참이고, 휴대폰 안 시험은 거짓이며 대신 `flow.localTest`(표시 전용, 상태 기계 입력 아님)로 알린다(§4.5 · §4.6 「차에서 테스트 요청」, 2026-11-07).
- 그래서 **짝지어진 동안 휴대폰은 꺼짐(OFF)이어도 `flow` 스냅숏을 늘 싣는다**(null 로 보내지 않는다). 기능을 꺼도 짝은 유지한다(§3.2). 휴대폰 `flow` 가 처음부터 null 이면 차는 설정을 모르는 것으로 보고 켜지 않는다. 한 번 받은 뒤 null 이 오면 직전 설정을 그대로 유지한다 — 휴대폰이 안 보이는 동안 감시를 끄지 않는 보수적 선택이다.
- **차가 주인일 때 휴대폰 스냅숏의 `owner` 는 `PHONE` 이 아니다**(`CAR`). 휴대폰 스냅숏은 설정 전달용이다. 차는 `owner:"PHONE"` 인 휴대폰 스냅숏만 넘김(이어받기)으로 읽되, 그 sync 직전에 차가 주인이 아니었고(처음 붙음, 또는 링크가 10초 넘게 끊긴 뒤 다시 붙음) 휴대폰 상태가 10초 안의 것(`serverTime − peer.receivedAt` 이 0 ~ 10,000)일 때만 이어받는다. 오래된 휴대폰 상태로 차의 흐름을 덮어쓰는 것을 막는다.
- (2026-10-30 확정 — 위 두 문장의 [추정]을 차 앱 `CarHub.onSyncSuccess` · `applySettings` 구현과 대조해 확정 문장으로 바꿨다.)
- 중계는 `flow` 안쪽(상태 · 주인 · 스냅숏)을 보지 않고 그대로 넘긴다 — 꺼짐 스냅숏도 막지 않는다(중계 시험 `test_phone_off_flow_snapshot_passes_to_car`).
- 주인은 응답의 고른 워치 상태 `ageMs` 가 30,000 을 넘으면 워치 판정을 쓰지 않고 「워치 신호 없음」 으로 다룬다(§4.3 신선도 규칙). 차 · 휴대폰 어느 쪽이 주인이어도 같다.

### 6.2 휴대폰이 중계에 못 닿아 주인이 된 경우(2026-10-30 · PM 결정)

- 차는 중계에 붙어 있고 휴대폰만 끊기면, 휴대폰은 차가 살아 있는지 알 수 없으므로 10초 뒤 주인이 되고(위 규칙) 차도 자기 링크가 살아 있어 계속 주인이다. 두 상태 기계가 같은 사건을 따로 열어 사건 id 가 1초쯤 어긋날 수 있다. **휴대폰이 직접 보호자 문자를 보내는 것은 맞다**(차가 살아 있는지 모르므로).
- 대신 문자를 실제로 보내는 곳은 휴대폰 하나라, **휴대폰이 보내기 직전에 같은 사건을 묶어 막는다**(`:shared` `GuardianSmsDedup`). 다시 붙은 뒤 받은 차의 문자 지시가 이미 보낸 휴대폰 문자와 같은 사건이면 보내지 않고 ack 한다. 원칙은 **놓침이 중복보다 나쁘다** — 묶기는 좁게 한다(be-qa 재현 A · B · C 뒤 PM 결정 2026-10-30).
- **같은 사건**(이미 보낸 기록 ↔ 보내려는 문자) — **테스트 표시(`test`)가 같고**, 아래 하나라도 맞으면. 테스트 기록과 실제 기록은 절대 묶지 않는다.
  1. 사건 id(`eventId`)가 같다.
  2. 보내려는 문자가 **받은 원격 지시(`from` 이 `PHONE` 아님 — 차)** 이고 이미 보낸 기록이 **휴대폰이 스스로 연 사건(`from:"PHONE"`, 자기 상태 기계)** 이며, 기준 시각(`EVENT` · `CANCEL` · `OBSERVE` 는 `firstAlertAt`, `ACCIDENT` 는 `accidentAt`)이 둘 다 있고 차이가 **60,000ms 이하**이고, 두 기준 시각 사이(앞 시각 초과 ~ 뒤 시각 이하)에 기록된 `CANCEL`(보낸 것 · 「보내지 않음」 모두)의 `responseAt` 이 끼어 있지 않다.
  - **휴대폰이 스스로 연 사건의 문자는 시각으로 막지 않는다(같은 id 만).** 차의 취소가 늦게 오는 동안 휴대폰이 연 진짜 새 사건을 삼키지 않으려는 것이다. 그래서 결함 3 순서(휴대폰 `EVENT` 먼저 → 차 `EVENT` 나중)는 한 통이고, 반대 순서(차 `EVENT` 먼저 → 휴대폰 자기 `EVENT`)는 두 통이 갈 수 있다 — 놓침보다 중복이 낫다. 취소도 같다 — 차 `CANCEL` 은 휴대폰 자기 사건의 `EVENT` · `CANCEL` 에 시각으로 묶이고, 휴대폰 자기 `CANCEL` 은 같은 id 의 `EVENT` 가 있어야 나간다.
  - 받은 차 지시끼리도 시각으로 묶지 않는다 — 한 주인은 한 사건에 kind 마다 한 번만 문자 지시를 내고 넘김 때 id 를 바꾸지 않으므로 같은 쪽의 다른 id 는 늘 다른 사건이다. 「사이에 취소 없음」은 휴대폰 사건이 응답으로 끝난 뒤 60초 안에 차가 연 새 사건을 삼키지 않게 한다.
- **판단** — 같은 사건에 같은 kind 를 이미 보냈으면 보내지 않는다(`DUPLICATE`). **같은 사건 id 의 `CANCEL` 기록(보냄 · 「보내지 않음」)이 이미 있으면 그 뒤에 온 `EVENT` 도 `DUPLICATE`** 다(2026-11-14 합동 점검 A-3 — 취소가 먼저 닿고 사건 문자가 늦게 다시 실린 경우. 같은 사건 id 에만 건다 — 위 규칙 2(60초 묶기)까지 넓히면 진짜 새 사건을 삼킨다). 「보냈다」는 실제로 보낸 기록(`sent`)만 센다. `CANCEL` 은 같은 사건의 `EVENT` 를 보낸 적이 있을 때만 한 번 보낸다(없으면 `NO_EVENT_SENT` — 보내지 않음). 둘 다 ack 한다.
- **동작 변경(2026-10-30 · PM 채택)** — 이전에는 `CANCEL` 지시가 오면 `EVENT` 를 보냈는지와 무관하게 보냈다. 이제는 `EVENT` 가 동의 없음 · 보호자 미등록 · 테스트 문자 거절 등으로 나가지 않은 사건이면 `CANCEL` 도 보내지 않는다 — 경보 문자를 받지 않은 보호자에게 취소만 가면 혼란스럽기 때문이다.
- **시계** — 기록의 시각은 모두 **휴대폰 벽시계**(에포크 ms)로 맞춘다. 문자 지시의 사실을 `WireFacts.toLocal` 로 휴대폰 단조 시각으로 되돌린 뒤(휴대폰 자기 지시 = `LOCAL` · 같은 기기 → 그대로, 또는 `SERVER` + 휴대폰 보정값 · 차 지시 = `SERVER` + 휴대폰 보정값) 같은 순간의 (휴대폰 벽시계 − 휴대폰 단조)를 더한다. 두 사건이 같은 길을 지나므로 중계 시계와 휴대폰 벽시계가 어긋나도(시험 ±90초) 그 차이는 상쇄된다. 되돌린 시각이 근사(「시계 미확인」 — 휴대폰 보정값이 없는데 `SERVER` 사실 등)이면 기준 시각을 null 로 두고 사건 id 로만 묶는다.
- 기록은 보낸 문자마다 남긴다(kind · eventId · from · 기준 시각 · 응답 시각 · test · 기록 시각 · `sent`). 테스트 문자는 사람이 확인해 실제로 보낸 뒤에만 `sent` 로 남긴다.
- **보내지 않은 `CANCEL` 도 응답 시각과 함께 「보내지 않음」(`sent:false`)으로 남긴다**(be-qa 4-2 · PM 결정 2026-10-30 — 차가 응답을 먼저 보고 곧바로 연 새 사건이, 버려진 차 취소의 응답 시각을 몰라 앞 사건에 묶여 삼켜지던 것). 같은 사건이라 안 보냄 · `NO_EVENT_SENT` · 보내기 실패 · 테스트 문자 거절 모두다(응답 시각이 없으면 남기지 않음). 이 기록은 「사이에 낀 취소」 판단에만 쓰고, 중복 · `NO_EVENT_SENT` · 「보호자 연락함」(`guardianContacted`) 판단에는 세지 않는다. 그 밖의 kind 는 보내지 않으면 남기지 않는다.
- **앱은 `:shared` 함수 둘만 부른다** — 보내기 전 `GuardianSmsDedup.decideAndRecord(기록, 새 기록, 지금 벽시계)`(24시간 정리 · 판단 · 「보내지 않음」 기록을 한 번에, 결과 목록을 그대로 저장), 결과가 `SEND` 면 보내기를 시도한 뒤 `afterSend(기록, 새 기록, 실제로 보냈는지)`. 새 기록은 `record(...)` 로 만든다(`Record` 생성자의 기록 시각에는 기본값이 없다 — 0 을 넣으면 바로 정리된다).
- **휴대폰은 보낸 보호자 문자 기록을 영구 저장소에 24시간 남긴다**(짝 보관과 같은 기간, PM 결정 2026-10-30 — 앱을 다시 켠 뒤 기록이 비어 `CANCEL` 이 `NO_EVENT_SENT` 로 빠지면 보호자가 계속 위급으로 오해한다). 저장 형식은 `:shared` `GuardianSmsDedup.encode` · `decode`(한 줄 문자열 `v2`, 옛 `v1` 줄은 `sent` 로 읽음, 깨진 줄은 버림), 정리는 `prune`(기록 시각부터 24시간 이하만 남김, 벽시계가 뒤로 가 미래 시각인 기록은 남김). 동의 철회 · 「모두 지우기」 때는 짝도 끝나므로 같이 지운다.
- [미검증] 실기기에서 휴대폰만 끊기는 경우의 사건 id 차이(1초 안팎)는 통합 시험(`SeamTest.phoneLinkLostOnly_singleGuardianSms`)의 가상 시계 값이다.

### 6.3 차의 짝 폐기(401, 2026-11-08 · PM 결정)

- 차가 401 을 받으면 토큰과 옛 짝의 흔적(워치 값 · 휴대폰을 본 시각 · 표시 설정 · 응답 기준 · 테스트 요청)을 지우고 다시 짝을 맺는다(`CarHub.onPairLost`).
- **경보 중(S1 · AP · S3 · S4 · S5)이 아니면**(OFF · S0 · 응답 뒤 S1R · S2) 상태 기계를 **꺼짐에서 새로 시작**하고 「시계 미확인」을 되돌린다. 켬 · 동의는 새 짝의 휴대폰이 다시 보낸다(§6.1). 경보 중이면 상태 기계를 그대로 두고 차 안 경보를 이어 간다.
- **주인 창은 바로 닫는다**(마지막 sync 성공 시각을 지움, 2026-11-09 PM 결정) — 10초를 기다리지 않고 그때부터 상대에게 낼 지시를 쌓지 않는다. 차 안 경보(음성 · 화면)는 이어 간다. 새 짝의 sync 가 성공하면 다시 주인이다.
- 보낼 지시 · 보낼 ack 는 비운다. 단 **보호자 문자 지시는 문자 보낼 함(§6.4 A-2)에 남겨 다시 짝지은 뒤에도 같은 지시 id 로 싣는다**(2026-11-14 — 아래 2026-11-09 의 「남긴 지시」 규칙을 대신한다. 차 앱이 보낼 함으로 옮기는 동안 아래 문장이 지금 구현이다). 다시 짝지은 휴대폰이 다른 휴대폰이면 휴대폰 방어(§6.4 A-3)가 「참여 전 사건」 문자를 막는다. 중복은 휴대폰의 `GuardianSmsDedup`(§6.2)이 막는다.
  - 남긴 지시는 **다시 짝지은 뒤 응답 `peer` 가 10초 안의 것(휴대폰이 붙음)을 처음 본 sync 다음에** 내보낸다 — 휴대폰이 붙기 전에 보내면 중계 큐 ttl(30초)이 지나 사라질 수 있다(2026-11-09).
  - 남긴 사건 문자(`kind:"EVENT"`)는 **그 사건이 응답으로 끝나면 지운다** — 보호자가 받은 적이 없으므로 그 사건의 `CANCEL` 도 보내지 않는다. 짝 폐기 때 같은 사건의 `EVENT` 와 `CANCEL` 이 둘 다 남아 있었으면 둘 다 버린다. `EVENT` 는 이미 옛 짝으로 나갔고 `CANCEL` 만 남았으면 `CANCEL` 은 남겨 보낸다(2026-11-09).
  - 사람이 「휴대폰 연결 끊기」를 고르면 남긴 지시도 모두 버린다.
- **한계(A-6)** — 사건 중 401 뒤 차 화면 응답은 휴대폰에 닿을 길이 없다. 그래서 사건 문자가 나가고, 다시 짝지은 뒤 대조(§6.4 A-3)가 취소를 보낸다. 운영 수칙(시연 24시간 안 다시 짝짓기 · 중계 재기동 금지)으로 막는다.

### 6.4 문자 전달 확인과 판정 주인(2026-11-14 · 합동 점검 A-1~A-5)

보호자 문자가 실제로 나갔는지 확인하는 곳은 휴대폰 문자 기록 하나다. 차는 문자 지시를 내는 순간 「보냄」이 아니라 휴대폰의 `flow.smsDone`(§4.5)을 보고 안다. 공용 판단은 모두 `:shared` 순수 함수다.

- **A-2 차 문자 보낼 함**(`GuardianSmsOutbox`) — 실제 `SEND_GUARDIAN_SMS` 만 담는다(테스트 문자 · 다른 지시는 지금처럼).
  - 사건 문자(`EVENT`)는 **넣은 뒤 만든 요청의 응답을 한 번 처리할 때까지, 상한 4초** 싣지 않는다. 그사이 같은 사건의 `CANCEL` 이 나오면 둘 다 버린다(만료 직전 응답의 사건 문자 → 취소 두 통을 막음, 한 방향 지연 1초에서 창 최대 2.75초 — be-qa 실행). 사고 · 관찰 문자는 보류하지 않는다.
  - 한 번 실린 것은 휴대폰 `smsDone` 에 `SENT` · `NOT_SENT` 가 보일 때까지 **같은 지시 id 로** 다시 싣는다(취소도). **한 요청 안에서는 사건 문자가 취소보다 앞**이다. 중계 `seen_ids` 가 ttl 안 중복을, 휴대폰 사건 id 중복 막기가 그 뒤를 막는다.
  - 주인을 내려놓아도 · 응답이 유실돼도 · 401 뒤에도 남긴다. 상한은 **사건이 끝난 뒤 10분**이다. 메모리 상태라 차가 다시 뜨면 사라지고, 그 빈자리는 A-3 이 메운다.
- **A-3 휴대폰 대조**(`CarSmsReconcile.step`) — 차 흐름 스냅숏과 휴대폰 문자 기록을 사건 id 로 맞춘다.
  - 차 흐름이 실제이고 `S3` · `S4`(사고는 `S5`)이고 응답 시각이 없고(사고는 보지 않음) 차가 문자를 냈다는데(`incidentSmsSent` · `accidentSent`) 같은 사건 id 의 그 종류를 **보낸 기록**(「보내지 않음」 기록은 세지 않음)과 취소 기록(보냄 · 「보내지 않음」 모두)이 없으면 **10초 뒤 휴대폰이 스스로 보낸다**(넘겨받을 때는 즉시).
  - 휴대폰이 사건 문자를 보냈는데 차 흐름에 응답 시각이 있고 같은 id 의 취소 기록이 없으면 **바로 취소를 보낸다**.
  - 이 길도 원격 상한 · 문자열 거르기 · 아래 방어 · `GuardianSmsDedup` 을 탄다.
- **원격 문자 상한(D-6, 사용자 확정 2026-11-14)** — 차 지시 · 대조 길 · 차에서 넘겨받은 사건의 실제 문자에 건다(휴대폰이 처음부터 연 사건은 밖). 문자 한 통마다(종류 · 사건 id 가 같은 문자의 다시 보내기는 한 번만) 세어 10분 3통 · 24시간 10통이고, **사고 문자는 일반 칸에 세지도 막히지도 않고 사고 칸에서 같은 값(10분 3통 · 24시간 10통)을 따로 센다**(40초 사이의 두 번째 에어백 전개는 사건 id 가 달라 나간다, PM 결정 27 — 결정 26 의 「사고 10분 1통」을 바꿈). 막힌 문자는 통보하고 `NOT_SENT` 로 싣는다.
- **보내지 못한 문자의 간격** — 같은 지시가 다시 오면(차 보낼 함 · 휴대폰 주인의 매 틱) 보내지 못함을 처음 본 때부터 **10초**가 지나야 다시 보낸다. 지시가 다시 오지 않으면 사건 · 사고 문자만 **60초 간격으로, 처음 시도부터 10분까지** 휴대폰이 스스로 다시 보낸다(같은 사건 취소를 받았거나 · 응답 시각이 생겼거나 · 꺼짐 · 철회면 멈춤, 위임 결정 3).
- **휴대폰 방어 둘**(`PhoneSmsGuard.check`, 위임 결정 4 · sec-audit) — 원격 지시와 대조 둘 다에 건다(휴대폰 자기 사건 제외).
  1. 사건 id 의 중계 시각이 **10분 넘게 지난 사건 문자**(`EVENT` · `ACCIDENT` · `OBSERVE`)는 보내지 않는다. 취소는 막지 않는다.
  2. 사건 id 시각이 **내 참여 시각보다 앞**이고 **내가 본 적 없는 사건**(내 문자 기록 가운데 실제로 보낸 기록 · 이번 참여 전에 본 흐름 — 「보내지 않음」 기록은 넣지 않는다, PM 결정 19)의 사건 문자는 보내지 않는다. 시각을 읽을 수 없는 id(`event-L…`)는 참여 전 사건으로 다룬다 — 단 **차 흐름이 중계 시계(SERVER)로 실은 그 사건의 시작 시각**(사고는 `accidentAt`, 그 밖은 `firstAlertAt`)을 본 적이 있으면 그 시각으로 참여 전을 가린다(sec-audit — 차 흐름은 요청마다 지금 보정값으로 다시 만들어진다). 그 시각도 모르면 지금 신선한 차 흐름의 진행 중 사건일 때만 허용한다(차가 중계 시각을 받기 전에 연 사고 문자를 막지 않게, app-phone · app-qa). **남는 한계** — 휴대폰이 그 사건을 LOCAL 시계 흐름으로만 봤거나 앱이 다시 떠 기억이 없으면 진행 중일 때 허용하므로, 그 좁은 창에서는 참여 전 사건을 가리지 못한다. 대조 길(A-3)에서는 휴대폰이 되돌린 사실로 지시를 만들기 때문에, 차 흐름이 LOCAL 시계였던 사건은 지시의 시각이 「지금」으로 잡혀 차가 묵은 뒤에도 같은 창이 남는다(sec-audit 최종 보고). 시각을 못 읽는 id 는 흐름에서 본 시작 시각을 알아도 1(10분 묵음)을 걸지 않는다 — 망이 늦게 돌아온 진행 중 사고 문자를 막지 않으려는 선택이고, 그만큼 묵은 L 꼴 사건 문자는 참여 전 판정만 거친다. 기준은 참여 시각이다(참여 직후 처음 본 흐름을 「본 사건」으로 치면 방어가 비워진다). 새 식별값은 싣지 않는다.
- **A-4 넘겨받기**(`Handover`)
  - 휴대폰은 마지막 실제 사건 흐름을 따로 쥐고, 차가 내려놓거나(`owner:"PHONE"`) · **경보 상태이던 차 흐름의 사건 id 가 사라지거나 바뀌거나**(`carIncidentLost` — 차 재시작 판별, 사고(S5)로 이어 가는 것은 제외) · 401 이면 넘겨받는다.
  - 차는 내 흐름에 진행 사건이 없고(OFF · S0) 신선한 휴대폰 흐름이 `owner:"PHONE"` 실제 진행 사건이면 받아들인다(`carMayAccept`). 휴대폰은 차가 같은 사건 id 를 `owner:"CAR"` 로 실을 때까지 넘겨주지 않는다(`phoneMayRelease`, 사건 임대). 차에 사건을 저장하지 않는다.
  - **다시 뜬 차는 신선한 휴대폰 흐름을 한 번 볼 때까지(상한 6초) 나쁜 손목 판정(`PULSE_WEAK` · `PULSE_ABSENT`)을 넣지 않고**(정상 · 착용 확인 판정은 넣는다 — 유예가 모두 막으면 S0 에 못 들어가 에어백 전이를 놓친다, PM 결정 16), 켬 · 동의도 신선한 휴대폰 흐름으로만 받는다**(`carWristAllowed` — app-qa 3차 실행, 유예가 없으면 3초 재시작에서 두 주인이 서로 다른 사건 id 를 쥠).
- **A-5 차 음성은 완료형을 쓰지 않는다** — 「보호자에게 알림을 보냅니다」(지금 문구), 휴대폰 연결을 확인하지 못하면 「…보호자 알림이 늦어질 수 있습니다」(`VOICE_S3/S4/S5_SMS_DELAYED`). 휴대폰이 확인하면 화면 줄만 「보호자에게 알림 보냄」(`SCREEN_SMS_CONFIRMED`), `NOT_SENT` 면 「보호자 알림을 보내지 않았습니다 · 휴대폰을 확인하세요」(원인은 말하지 않음).
- 차 · 휴대폰 연결은 2026-11-14 에 들어갔다. 문자 0통 경우를 재현하는 통합 시험은 `integration` `RootBundleTest` 11개이고 모두 켜져 있다.

## 7. 오류

| HTTP | `error` | 언제 |
|---|---|---|
| 400 | `BAD_REQUEST` | JSON 이 아님 · 객체가 아님 · 짝 없는 서로게이트 · `NaN`/`Infinity` · 범위를 넘는 수(`1e999`) · `to` 가 생략 · null 이 아닌데 정한 값이 아님 · 필수 필드 형이 틀림 · `seq` · `sentAt` · 휴대폰 `responseAt` 이 Long 범위(−2^63 ~ 2^63 − 1) 밖 · `role` 이 생략 · null 이 아닌데 `PHONE`/`WATCH` 가 아님 · 휴대폰 `responseAt` 이 정수 · null 이 아님 · 휴대폰 `carDisplay` 가 객체 · null 이 아님 · 지시 형식 틀림(type · ttl · from · to · id 길이 · 개수) · `AMBIENT` 지시의 `payload.mode` 가 `"BLUE_RED_BLINK"`(대소문자 무시, 법률 검토 전 금지(G6) — 중계도 거부, 요청 전체를 거름) |
| 401 | `TOKEN_INVALID` | 토큰 없음 · 틀림 · 다른 역할 토큰(`pair/code` 는 차 토큰만) · 짝 만료(24시간) · 짝 종료 뒤 · 참여한 역할이 없고 살아 있는 코드도 없어 지워진 짝 · 한 번도 참여한 적 없이 첫 코드가 만료돼 지워진 짝(§3.1) · 같은 역할이 새 코드로 다시 참여해 바뀐 옛 토큰 |
| 404 | `PAIR_CODE_INVALID` | 코드 없음 · 만료(10분) · 그 역할로 이미 씀 · 실패가 5번 걸려 버린 코드(§3.1.1) |
| 404 | `NOT_FOUND` | 없는 경로 |
| 405 | `METHOD_NOT_ALLOWED` | 경로는 있으나 메서드가 틀림(`/v1/health` 는 GET, 나머지는 POST) |
| 413 | `BODY_TOO_LARGE` | 본문 64KB 초과 |
| 429 | `RATE_LIMITED` | 짝짓기 빈도 제한에 걸림(§3.1.1 — 주소별 `pair/join` 실패 · 주소별 `pair/start` · 주소별 살아 있는 짝 8개(밀어낼 조용한 짝 없음) · 짝별 · 주소별 `pair/code`). 짝 · 토큰은 그대로다 |
| 500 | `INTERNAL` | 서버 내부 오류(응답 인코딩 실패 포함) |
| 503 | `CAPACITY` | 짝이 64개(`--max-pairs`) 차서 `pair/start` 를 받을 수 없음 |

오류 본문은 늘 `{"error":"<코드>"}` 하나다. 401 을 받으면 앱은 짝짓기를 다시 하고, 그 밖의 오류 · 연결 실패는 다음 주기에 다시 보낸다.

- 잘못된 HTTP 버전(예 `HTTP/2.0` 요청 줄)에 대한 505 와 깨진 요청 줄에 대한 400 은 파이썬 `http.server` 기본 동작이다. 이 둘은 본문이 JSON 이 아니고(HTML), 위 표 형식을 따르지 않는다.
- 소켓 읽기 제한 시간은 **10초**다. 머리나 본문이 10초 안에 다 오지 않으면 응답 없이 연결을 끊는다.
- 요청 하나(기다림 · 머리 · 본문 · 응답)에 **전체 마감 20초**(`--request-deadline-sec`)가 있다. 조금씩 보내며 버티는 느린 요청도 마감에 응답 없이 끊는다(2026-11-13).
- **동시 연결은 256개**(`--max-conns`)까지다. 넘는 연결은 응답 없이 바로 닫는다. 클라이언트에는 연결 실패와 같아 다음 주기에 다시 보낸다.
- 앱의 처리(2026-11-13 확인, 코드 동결이라 바꾸지 않음) — 세 앱 모두 401 만 짝 폐기로 다루고, 429 · 503 · 연결 끊김은 일반 실패로 보고 다음 주기(또는 사용자의 다시 누름)에 다시 보낸다. 휴대폰 짝 참여 화면은 429 를 「번호가 틀림」 문구로, 워치 참여 화면은 「네트워크」 문구로 보인다.

## 8. 개인정보 규칙(G2 · G3)

- 중계는 **메모리에만** 보관한다. 디스크 · 파일 · 데이터베이스에 쓰지 않는다. 서버를 끄면 모두 사라진다.
- 접근 로그에는 **메서드 · 경로 · 상태 코드 · 처리 시간만** 남긴다. 본문 · 토큰 · 짝 코드 · 위치 · 심박 · 주소 · 차종을 남기지 않는다. 없는 경로는 경로 대신 `-` 로 적는다(경로에 토큰을 넣어 보내도 남지 않게). 질의 문자열은 버린다. 내부 오류와 연결 오류는 예외 종류 이름만 남긴다. 이 규칙은 서버 시험(로그 캡처)으로 고정한다.
- 보관 기간은 짝 24시간이 끝이다. 동의 거부 · 철회와 「모두 지우기」는 `pair/end` 로 즉시 지운다. 기능 끄기는 짝을 유지한다(§3.2 — 꺼짐 설정 스냅숏만 오간다).
- 위치(`naviLat/Lon` · `naviAddress`)는 위치 제3자 제공 동의가 있을 때만 싣는다. 없으면 null 로 보낸다(G3).
- **휴대폰 위치는 중계로 보내지 않는다**(2026-11-08 · 감사 중4 A 안 — 차가 읽지 않는 값을 보내지 않는 G2 최소 전송). 휴대폰 위치는 그 휴대폰이 보내는 보호자 문자 · 119 작성 본문의 위치 줄에만 쓴다.
- 워치 값은 건강 관련 별도 동의가 있을 때만 싣는다. 없으면 휴대폰은 `watch:null`, 워치 직접 경로는 쓰지 않는다(G2). 특히 **심박 정수 `hr` 는 건강 관련 별도 동의가 있을 때만 보내는 값**이다(PM 결정, G2 를 그렇게 고친다).
- **휴대폰 건강 동의 전파(2026-11-08 · 감사 하4)** — 건강 동의는 휴대폰 · 워치에 따로 있다. 휴대폰은 sync 마다 `healthConsent` 를 싣고, 그 값이 `false` 면 중계는 워치 직접 경로 값과 휴대폰 경유 값을 보관하지 않아 차 · 휴대폰 응답의 `watch` · `peer.watch` 가 null 이다(워치 직접 sync 는 200 으로 받고 받은 시각만 남겨 `watchDirectAgeMs` 는 계속 계산 — 보관 규칙 §5). 휴대폰에서 건강 동의를 끄면 워치가 직접 보내도 차로 내려가지 않는다.
- 차 앱은 받은 워치 값 · 위치를 저장하지 않는다(화면 · 판정에만 쓰고 버린다).
- **차 화면 표시(2026-11-01)** — 차는 건강 관련 동의가 있고 `carDisplay.hideHr` 가 `false` 일 때만 심박 · 맥박 신호 상태를 화면에 보인다. 숨김 설정을 모르면 숨긴다(§4.1 `carDisplay`). 휴대폰 동의 ② 문구에 「연결한 차 화면(표시만 · 저장하지 않음)」을 받는 곳으로 적었다(동의 문구 판 2). 판 1 로 동의한 사용자의 이전 동의는 원래 목적(감시 · 보호자 · 119)을 덮으므로 다시 동의하기 전에도 **감시 · 워치 값 전송 · 문자 · 119 는 그대로 동작**하고, 동의가 없는 새 목적 「차 화면 표시」만 막는다 — 휴대폰은 사용자 스위치와 따로 `carDisplay.hideHr:true` 를 보낸다. 다시 동의하면 스위치 값을 따른다(PM 판단 2026-11-01 — 업데이트로 감시가 조용히 꺼지는 놓침을 막는다. 재동의가 법적으로 꼭 필요한지는 [법률 검토 필요]).
- 베타는 LAN 평문 HTTP 라 같은 Wi-Fi 안에서 엿볼 수 있다. 실제 건강 · 위치 값 대신 **테스트 모드(시뮬레이션) 위주**로 시험하고, 공개 운영은 HTTPS 서버로만 한다.
- 짝 코드는 6자리라 10분 안에 대입 시도가 가능하다. 베타(LAN)에서는 받아들이고, 운영 전에 시도 횟수 제한을 넣는다 [운영 전 과제].
